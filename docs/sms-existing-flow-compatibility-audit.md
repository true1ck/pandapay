# Existing SMS flow: compatibility audit and regression gates

Reviewed against the 21 October 2026 working tree. This audit supplements the [master implementation plan](SMS_INTELLIGENCE_MASTER_IMPLEMENTATION_PLAN.md). Its purpose is to preserve the behavior users already depend on while the new fact pipeline and Gemini worker are introduced. These are code-read findings, not a claim that the proposed implementation has passed tests.

## Existing end-to-end behavior to preserve

| Stage | Current implementation | Contract to retain |
| --- | --- | --- |
| Login/onboarding | `app/lib/features/onboarding/permissions_screen.dart` requests SMS permission, starts the shared controller, scans the existing inbox locally, then syncs in the background. `app/lib/app/router.dart` mounts `smsBackgroundFlushProvider` and `smsListenerLifecycleProvider` from the authenticated shell. | After permission and login, detection starts without opening the SMS import screen. Onboarding does not wait for network to finish before showing local results. Permission refusal/revocation leaves the rest of the app usable. |
| Startup/resume/auth restoration | `smsBackgroundFlushProvider` starts the listener, captures newer inbox rows, drains pending local SMS, and retries old review rows when the parser version changes. Calls are coalesced while one pass runs. Online restoration triggers a retry. | Startup, resume and auth restoration may overlap without launching duplicate scans or uploads. Retry network work without resetting inbox progress. |
| Initial and incremental inbox scan | `SmsInboxScanner` snapshots the Android provider's highest row ID, reads bounded ascending pages, commits `sms_inbox_progress` **after** each successful local page capture, then later reads only IDs greater than the per-namespace checkpoint. Nonfinancial rows advance the checkpoint too. | First scan covers eligible existing messages once; later passes only scan new provider IDs. A failed page resumes from the last committed page. A message arriving mid-scan is eligible on the next pass. No API failure rewinds this cursor. |
| Live foreground and background | `SmsAutoImportController` registers one foreground listener; the background handler writes locally without auth/network. Broadcast capture does not advance the inbox cursor. | Live capture is immediate locally; background capture is recoverable on next open; inbox and broadcast delivery of the same SMS converge. Do not put credentials or Gemini calls in the Android background isolate. |
| Local durable intake | `SmsIntakeRepository` keeps `sms_captured_messages` and an append/ack `sms_intake` outbox. `SmsImportStore` saves observations and provisional transactions. Failed uploads stay pending with retry backoff; an arrival during upload survives the older item's acknowledgement. | Capture and local display work offline. An item is marked processed only after a resolved or reviewable outcome. Server/AI unavailability never deletes local evidence. |
| Source idempotency | `smsSourceKey` and `api/src/import_source_key.js` use user/profile + normalized sender + normalized body; they deliberately ignore delivery timestamp. Receipts and server transaction observations prevent exact replay. | Keep existing key values and receipts valid during migration. One live/inbox/backup replay creates one source and one economic event. Never use the raw SMS text as an admin-visible key. |
| Namespace/account switch | Inbox progress, captured rows, intake, receipts and review items are namespaced. Capture and upload check that the active account has not changed. Signed-out/legacy recovery is handled separately. | No SMS, pending job, review task or projection may appear under the next signed-in account. Preserve pending legacy recovery and do not bulk-migrate signed-out data automatically. |
| Server backfill and side effects | `syncPendingMessages` uploads older messages as backfill before current-month messages, with billing priority; historical spend skips current-cycle reward/cap/milestone side effects. Server batch size is capped at 200. | AI queue order must not rewrite accounting date or trigger current-cycle notifications/rewards for historical imports. Preserve statement/due-day ordering and the 200-item HTTP import contract until a versioned replacement exists. |
| Reconciliation and Needs Review | `onSmsUploaded` fetches a transaction window once per batch, replaces provisional rows with confirmed ones, acknowledges known negative results, and files unresolved messages in local Needs Review. A review replay runs once per local-parser version/account. | No provisional+confirmed duplicate in Spending. A parser upgrade can improve old review items without recreating already resolved transactions. User-confirmed/dismissed items are protected from late AI results. |
| Backup import and card discovery | Backup import filters, groups by suffix, sends 200-item chunks and sends unresolved items to Needs Review. Card discovery reads captured bodies through the shared controller and does not start an independent full inbox scan. | Reimport does not create duplicate spends. Card discovery remains responsive and does not rescan history. Preserve user selection and ambiguous-suffix behavior. |
| Product screens | Home balance uses latest observed balance; Payments Due uses local bill observations plus payment transactions; commitments and recurring screens have distinct paths. | New facts must update all relevant projections without changing existing correct totals, bill state, or timestamp semantics. |

## Migration hazards and required handling

1. **Widening the prefilter will not revisit older excluded rows.** The current inbox cursor advances across *all* Android provider IDs, including messages filtered out by `looksLikeTransactionSms`. Do not reset `sms_inbox_progress` to zero when adding balance/mandate/card families. For historical discovery, run a separately checkpointed, bounded, opt-in or versioned backfill over older provider IDs or use stored captured messages where available; dedupe with existing source keys. Live/new SMS detection can change immediately without touching old progress.
2. **Do not change the existing source hash in place.** `smsSourceKey` and `importSourceKey` are part of local receipts, server observations and backup replay. New fact IDs should derive from the **existing source key plus stable fact type/role/source slot**; reordering parser outputs must not create new IDs. If a future identity scheme is needed, keep an alias table to old keys and prove zero duplicate projections before migration.
3. **Identical text can represent two separate alerts.** The current source key intentionally collapses same sender/body for live/inbox dedupe, even if that exact SMS is sent again days later. That is an existing limitation, especially for balance-only notices without a bank reference. Record it as a distinct-source edge case. Explore Android provider ID, explicit transaction reference and a conservative receive-time separation *in a versioned source-identity design*; do not append timestamps to the current hash and thereby break replay protection. A balance snapshot with the same amount/date may be harmless to collapse, while two actual identical purchases would not be.
4. **`localIgnore` is broader than disposable noise.** Local autopay setup and balance-only notices are acknowledged after saving an observation. They must not become posted spend or recurring purchases. When the new server needs these facts, sync a typed fact or apply it locally, without blindly uploading the same SMS again or putting it in transaction review.
5. **The old server API is transaction shaped.** `/transactions/from-sms` and `/batch` currently run bill-day and mandate side effects around a transaction parse. Add the new observation API/response compatibly or adapt behind existing methods; preserve old client behavior and avoid double-running day/limit/mandate updates while both paths coexist.
6. **Review replay is version gated.** Startup retries current Needs Review once per parser version/account. New model/rule versions should reprocess only eligible unresolved tasks and **never** a user-confirmed or dismissed task. Store replay/version state independently from Android inbox progress and AI job retry state.
7. **Payload retention changes the existing disclosure.** `sms_consent_screen.dart` currently says SMS text is never stored on PandaPay servers. A durable AI queue with encrypted short-lived text would make that line inaccurate. Update this copy and onboarding copy before enabling the worker. Keep the existing automatic login flow; do not add a per-message prompt. Document provider forwarding, retention and the off switch.
8. **The screenshot exposes current false-review cases.** A transaction-verification alert, Kotak Neo settlement payout and call-forwarding notice appear as generic transaction candidates. Add these to the negative/financial-kind corpus; classify them correctly without changing the scan cursor or review store identity.
9. **Signed-out/background ownership is a special case.** The background handler writes under the last namespace stored in preferences, defaulting to `signed-out`; legacy preference rows have an explicit recovery path. Test logout/account-switch races and avoid moving a signed-out or legacy SMS into a new account without the existing recovery decision.

## Compatibility test matrix for each implementation phase

| Scenario to simulate | Expected observable result | Existing baseline / new test |
| --- | --- | --- |
| Fresh login with permission and 1,000 mixed inbox rows | One paged local scan, only eligible financial messages captured, local UI available before server; cursor reaches provider head. | Extend `sms_inbox_scanner_test.dart` and onboarding/controller tests. |
| Second app open with no new SMS | Zero history pages; no new server/Gemini jobs, spend rows or review tasks. | `sms_inbox_scanner_test.dart`, `sms_capture_pipeline_test.dart`. |
| One new SMS after initial scan | Reads only IDs above checkpoint; one source, relevant facts, one final outcome. | Scanner/controller tests. |
| Foreground broadcast then same inbox row | One source and economic event; inbox checkpoint still advances. | Intake, controller and server idempotency tests. |
| Background delivery while closed, followed by resume | Local row already present, one upload after auth restoration; no direct background API call. | Background queue/worker tests. |
| Offline first scan and several failed API attempts | Local observations/provisional state visible, cursor fixed, outbox retained, backoff works; reconnect drains it without another history scan. | Existing `sms_capture_pipeline_test.dart`; extend for AI job acceptance. |
| Crash between page capture and checkpoint | Page may replay once; source/fact/transaction count remains one. | Existing scanner interrupted-page case plus fact-store test. |
| Crash between server job acceptance and device ack | Retried POST returns same job/result; no second Gemini job or economic event. | New API/queue integration test. |
| Two accounts on the same device and a switch during capture/upload | Separate cursors, receipts, review and jobs; old result cannot attach to new account. | Existing scanner account-switch cases plus API response race test. |
| Inbox plus backup-file import of same SMS | One source/economic event; backup summary reports duplicate; no second bill cycle or balance history row. | Backup and source-key tests. |
| Repeated exact sender/body days apart | Document current collapse; new source-identity experiment must distinguish true repeat while still folding broadcast/inbox copies. | New edge-case fixture; do not silently alter legacy key. |
| Parser/rule update after user confirmation | Reprocessing updates only unconfirmed facts; no review resurrection or user override loss. | New replay/override tests. |
| Old historical SMS during current month | Correct bank-reported transaction date; no current reward/cap/milestone/notification side effect. | Existing backfill tests plus AI projection tests. |
| Gemini 429, timeout or malformed grouped response | Job remains durable and retries within budget; only unresolved item moves to Needs Review; app never rescans inbox to recover it. | New worker/queue tests. |
| Balance-only, mandate-only, bill+offer, security and marketing SMS | Correct non-spend facts or safe exclusion; no misleading transaction review, no duplicate screen rows. | New shared family fixtures. |
| Permission revoked and restored | No unauthorized scan/upload while off; resume once restored catches newer inbox IDs without cursor reset. | New lifecycle/permission test. |

## Existing tests to preserve

Before merging each phase, run the relevant current tests: `app/test/features/sms_import/sms_inbox_scanner_test.dart`, `app/test/data/sms_capture_pipeline_test.dart`, `app/test/data/local/sms_intake_repository_test.dart`, `app/test/data/local_first_sms_test.dart`, `app/test/features/sms_import/sms_background_queue_test.dart`, `app/test/features/sms_import/sms_backup_import_screen_test.dart`, `app/test/data/card_bill_ledger_test.dart`, `api/test/sms_parser.test.js`, `api/test/subscription_parser.test.js`, and the due-day/import-resolver/recurring suites. Expand tests only at affected seams and require a scenario assertion for every migration hazard above.

**Release gate:** if login auto-detection, incremental scan, duplicate suppression, offline recovery, account isolation, historical backfill semantics, or user override precedence regresses, stop rollout of the new pipeline even if Gemini classification accuracy improves.

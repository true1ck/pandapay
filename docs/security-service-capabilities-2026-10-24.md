# Service capabilities and Google identity — 24 October 2026

This is the R4/R5 source follow-up to the [remaining implementation plan](security-remaining-implementation-plan-2026-10-23.md). It is a local candidate, not a deployment record. Existing notification edits, data UUIDs and encryption keys are preserved. Database changes must use the canonical transactional migration runner with writer fencing and paired recovery.

## What changes

| Flow | Source behavior | Compatibility and release gate |
|---|---|---|
| Partner conversion webhook | A separate login can execute one private ingestion function. The HTTP signature and 202 matched/unmatched contract remain. Inputs are bounded, payload storage is allowlisted, and concurrent retries without a reference reuse one stable row. Existing duplicate rows are preserved. | Provision and verify the dedicated login before releasing an active callback integration. Missing configuration returns 503 and never falls back to the app/owner pool. Partners reporting multiple conversions for a click must supply distinct nonempty references. |
| Backup status | Reader exposes only timestamps, size, verification/storage state and caller-owned conflicts. Legacy stub successes and raw paths/errors never qualify. Manual requests remain 409; an actual status-service failure is 503 so current clients can retry. | Until a fresh verified set is explicitly published, status is unavailable. Evidence becomes stale after 48 hours; at most 32 sanitized attestations are retained. No backup files are deleted by status retention. A local copy is labeled local. |
| IMAP polling | A dedicated restricted worker enumerates at most 100 active connections per batch. A private durable UUID cursor rotates through batches across process changes. Use a direct/session-affine PostgreSQL URL; transaction pooling cannot preserve a session advisory lock. The worker pool has two bounded connections: one for polling and one available for readiness. A five-minute budget is checked between sequential mailbox requests; a request already underway retains the connector's existing deadline. Deferred/failed records keep their successful-poll timestamp. A worker-only cursor function resumes after the last attempted connection when the cycle deadline is reached, so a short batch cannot starve later mailboxes. |

## Separate credentials and role boundaries

These are environment variable names and locations, not secret values. Put real values in the protected deployment/recovery configuration, never in tracked Markdown or client builds. No new live credential has been generated by this source task.

| Variable | Used by | Scope |
|---|---|---|
| `PARTNER_WEBHOOK_DATABASE_URL` | API callback pool | Dedicated `partner_webhook_runtime` login, member only of `pandapay_partner_webhook`; maximum two pool connections. |
| `PARTNER_WEBHOOK_DB_PASSWORD` | Privileged migration bootstrap only | Creates the dedicated login when explicitly set; reruns preserve an existing credential. |
| `IMAP_POLL_DATABASE_URL` | API's opt-in polling worker | Dedicated `imap_worker_runtime`, member only of `pandapay_imap_worker`; maximum two pool connections. |
| `IMAP_WORKER_DB_PASSWORD` | Migration bootstrap only | Creates the dedicated worker login when explicitly set. |
| `BACKUP_STATUS_WRITER_DB_PASSWORD` | Migration bootstrap only | Creates `backup_status_runtime`, member only of `backup_status_writer`. Never give this authority to the API or a mobile client. |
| `BACKUP_STATUS_DATABASE_URL` | Explicit recovery-machine publisher | Dedicated status writer URL. Strict TLS is the default; local synthetic fixtures explicitly opt out only on loopback. |
| `BACKUP_STATUS_AGE_IDENTITY_FILE` | Recovery-machine publisher | Existing protected age identity; do not copy it to the backup-only host. |
| `AUTH_SECURITY_ADMIN_DATABASE_URL` | Explicit dashboard-access operator command | Privileged auth operator connection, separate from auth runtime. |
| `AUTH_RUNTIME_ROLE` | Migration job | Existing scoped auth login. New grants are SELECT/INSERT on provider links and, when the dashboard is enabled, read-only capability lookup. This does not finish whole-auth-schema role provisioning. |

Private function owners are NOLOGIN, NOSUPERUSER and NOBYPASSRLS with narrow table privileges and explicit RLS policies. Reader/writer/worker capabilities cannot SET the owner role. Functions use fixed search paths and revoke PUBLIC execution. Managed PostgreSQL role ownership setup temporarily enables only the migration role's required SET permission, then restores its previous membership options. The canonical runner's transaction is required; do not execute individual fragments out of order.

Runtime service readiness rejects broad role attributes or direct credential/table access. Optional service URLs remain blank until that integration is configured. Dedicated partner and IMAP logins add at most four API pool connections in total; include them in the existing free-host connection budget. Migrations do not rotate an existing login password automatically. Wrong/mismatched credentials must fail readiness and be corrected before release.

## Publishing truthful recovery status

1. Run a fresh paired-v5 restore drill on a separately controlled disposable recovery target using the existing key material. The new proof records the exact manifest/product/auth ciphertext SHA-256 values after verification. Old set-ID-only markers are insufficient for publication.
2. On the recovery machine, provide the dedicated publisher URL and existing age identity through protected configuration. Run `node db/scripts/publish_backup_status.js --set-dir /absolute/path/to/complete-set-id`.
3. The publisher reads only fixed filenames, streams hashes, checks completion/proof freshness and same-set/digest binding, decrypts the manifest in memory and checks both database inventories. It rejects incomplete, stale or changed evidence and broad database identities. Plaintext metadata, keys and database credentials are not emitted to routine output.
4. Verify the API projection under an ordinary authenticated profile. `applicationCheck:not_run` stays explicit; a database restore alone is not reported as full application or upgrade acceptance. No automatic status-publication schedule is configured by this source task.

## Provisioning dashboard access

Keep `ENABLE_ADMIN_DASHBOARD=false` until migration/runtime permissions and an intended operator are reviewed. With a protected `AUTH_SECURITY_ADMIN_DATABASE_URL`, the operator command is:

```text
node auth/scripts/security_admin_access.js grant EXISTING_UUID EXPIRY_ISO_UTC
node auth/scripts/security_admin_access.js revoke EXISTING_UUID
```

Grant locks/checks the active verified account; revoke locks an existing account in any state. Membership updates are transactional. Revocation/expiry/deleted or inactive account state denies access. It does not create an account or change the account's role. No live operator membership was added during implementation.

The full-suite candidate and the four later custody-only source/test differences are explicitly recorded in the source manifest; the later changes passed the focused suite. Five isolated Android API 37 tests pass in the separate `app.pandapay.keycipherfixture.pandapay` package:

1. Real secure-storage key creation/reopen and install binding, with the cross-isolate provisioning lease.
2. Encrypted file/WAL, correct-key reopening, wrong/missing-key refusal, transaction rollback and damaged-page rejection.
3. Complete current `AppDatabase` schema copied encrypted, including guest/account profile data and a pending mutation retaining its original ID. A second writer is refused during the source fence; the source is unchanged after success and remains writable afterward.
4. Rich SQLite data copied with raw non-UTF-8 text bytes, blobs, generated columns, `WITHOUT ROWID`, views/indexes and a retained AUTOINCREMENT high-water mark. Low-disk admission and cancellation after the first copied row preserve the source.
5. Receipt encryption and scoped viewing, original-file preservation, wrong-account refusal and preexisting output preservation.

The native fixture uses `sqlite3` 3.5.2 with its maintained SQLite3MC hook. A plain engine rejects conversion before creating a destination. The current app dependency manifest/lock remains unchanged. Final receipt-key custody and metadata-size/field hardening are covered by the host focused suite; the recorded native manifest identifies exactly which source was exercised. The test disk callback explicitly admits **synthetic fixture data only**, not production storage. Tests do not prove physical flash erasure, full signed-device acceptance or a no-loss application switch.

The first Android key test caught a legitimate OS alias in the path-provider app-support directory. The production lease factory now resolves that trusted OS-provided location before applying its strict injected-path checks. A later fixture SQL literal used double quotes, which the new engine correctly refused as an identifier; it was fixed to standard single-quoted SQL. Both failures were resolved before reporting the native pass.

## Why the copy uses SQL

The initial native backup-API cross-encryption experiment was refused by the encrypted engine. The implementation therefore reconstructs the reviewed schema and streams typed rows under the source fence, then compares complete contracts before and after reopening. Text bytes travel as blobs with an explicit target TEXT cast, so invalid UTF-8 is preserved; storage classes remain in the digest. Triggers are installed after row copying, preventing data from being processed twice during staging. Unique/foreign-key/integrity and schema/data checks retain their original semantics.

The [SQLite backup documentation](https://www.sqlite.org/backup.html) describes snapshot/locking behavior. [SQLite3MC configuration](https://utelle.github.io/SQLite3MultipleCiphers/docs/configuration/config_sql_pragmas/) requires the key before data access and a real query to verify it. The staged copy selects ChaCha20, uses a random install key and memory temporary storage; it does not use a user password or service credential.

# Scoped journal and acceptance contract

Version `1.0.0-foundation`; internal pure domain boundary. This extends the existing foundation without enabling commands, source funding or shared writes. Owner: root. Requires independent financial/security and real database verification before activation.

An expense revision is the exact validated input to `projectExpense`, plus immutable metadata/source/consent fields in the command layer. Persist its member order and projected obligation edges. The accepted head changes only after every required financially affected member approves the exact revision hash and previous head version. An edit invalidates earlier approvals. Author-recorded proposals are private/provisional and never produce one-sided accepted debt. Membership/account claiming is not financial approval.

All journal/projection operations have one immutable `contextId` and `currency: INR`. Member IDs follow the foundation opaque ID grammar. A group/direct context has at most 200 identities. No cross-context or cross-currency offset, no global netting and no automatic debt simplification. A zero net member/group balance does not imply settled: A→B, B→C, C→A remain three obligations.

`expenseRevisionDelta({contextId,currency,previous,next})`: `previous`/`next` are null or full snapshots; both null is invalid. Null next means an explicitly approved void, not deleting a bank transaction. Project both validated snapshots independently, subtract the previous frozen edges and add next edges. Output `{contextId,currency,members,pairs}`. Members are sorted unique `{memberId,balanceMinor}` signed deltas. Pairs are sorted unique `{lowMemberId,highMemberId,balanceMinor}`, `low < high` in ASCII order. Positive pair value means high owes low; negative means low owes high. Omit zero pairs and zero member deltas that have no incident pair; retain an incident zero member delta so circular/refund counterparty structure remains validated. Exact delta member balances must agree with pair incidence and sum zero.

`settlementDelta({contextId,currency,payerId,receiverId,amountMinor,direction})`: positive canonical amount within the single-expense cap; payer≠receiver; direction `confirm` or `reverse`. Confirm adds amount to payer member position and subtracts from receiver, reducing the existing pair obligation; reversal emits its exact inverse. This helper does not confirm a payment or authorize reversal. Only the command layer can apply an agreed/verified immutable event once, with original payment identity and receiver confirmation/provider evidence. UPI launch/callback/screenshot is insufficient. Original payment events/allocation receipts remain immutable when an expense changes or is voided.

`applyBalanceDelta({current,delta})`: canonical same-context/currency envelopes in the above format; missing current state uses empty arrays. The state is a bounded current projection, not unbounded journal replay. Validate canonical IDs/pair ordering, unique rows, signed canonical decimal strings (`0` or `-?[1-9][0-9]*`, no `-0`), magnitude ≤ aggregate cap and pair/member incidence. Apply once transactionally under operation/effect uniqueness outside this function. At most 200 members and 19,900 pair rows; output sorted current rows, retaining zero member identities but omitting zero pairs. The sum of absolute active pair balances per context also stays within the aggregate cap, bounding gross owed/owing even in a zero-net circular graph. Across-context summaries require their own checked aggregate and must not truncate. Overflow rejects the whole operation; no mutations. Envelopes are closed shapes. Stable extra error codes: `INVALID_BALANCE`, `INVALID_BALANCE_PAIR`, `BALANCE_MISMATCH`, `CONTEXT_MISMATCH`, `INVALID_SETTLEMENT`, `INVALID_SETTLEMENT_DIRECTION`, `INVALID_OBLIGATION_COUNT`.

`allocateSettlement({amountMinor,obligations,allocationOrder})`: up to 100 unique obligation rows `{obligationId,outstandingMinor}` within the aggregate cap, exact ID permutation. Allocate a positive capped payment to this caller-authorized pair/context/currency in the persisted selected order, preserving the original allocations. Output `{allocations:[{obligationId,amountMinor}],creditMinor}`; zero allocations omitted, any excess is explicit pair credit. Zero outstanding rows allowed. No loop grows with money amount. Pair/context/currency authorization and original event uniqueness are command-layer requirements. Never route excess to a different friend/group.

For a revised ₹1,200 bill, three ₹400 shares, after friends each pay ₹400: accepted revision decreases to ₹900 with three ₹300 shares. Previous confirmed payments stay; new outstanding is you owing Rahul ₹100 and Priya ₹100. An approved void leaves you owing ₹400 to each. If A paid B then a correction changes creditor to C, show B→A refund and A→C debt; never silently replace them with B→C.

On the server: lock established sorted `transaction-ingest:<sourceOwner>` locks before context/reservation/expense locks; lock stream heads before incrementing a committed cursor. Canonical legacy/v2/foreign aliases share one funding reservation. Recheck current owner/type/posted purchase leg/instrument/source version and confirmed INR foreign valuation in the same transaction. Accepted sharing survives source retraction; new funding pauses pending reviewed correction. Never infer eligibility from `entry_kind=spend` or event complete/user_confirmed alone.

Production writes require durable actor-scoped operation ID+canonical request hash, unchanged replay result with reauthorization, permanent financial-effect uniqueness, revision preconditions and source/head locks. API/local commands cannot coalesce financial payloads, erase payment history or acknowledge a proposal as accepted. Partial payments stay partially owed; overpayments/corrections produce explicit pair credit, not consumption/rewards.

Projection algorithm identity is frozen as `pair_v1`: persisted accepted revisions retain their projected edges and edge hash. The implementation behind this v1 helper must never silently change its matching policy. A future engine needs a new version and explicit migration/compatibility dispatcher; P03 subtracts stored prior edges and verifies them against the pinned algorithm before accepting a correction. Projection version is not permission to reroute existing obligations.

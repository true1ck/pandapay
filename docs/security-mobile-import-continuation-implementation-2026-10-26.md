## Flow implemented

1. The customer reviews a file import and taps import. With the new build flag enabled, the app prepares the entire bounded plan and encrypts its exact batch bodies before sending the first request. Existing destination, batch and row idempotency keys remain.
2. The foreground runner submits one saved batch at a time through the existing authenticated `POST /statement-imports`. A live SQLite lease and account/recovery gate prevent overlapping local sends. The request owns its transport and deadline; the runner waits for the actual HTTP future to settle before releasing admission.
3. The app removes a batch's encrypted payload only after a 200/201 response with `receiptVersion:1` and complete, consistent result counters. Successful result metadata remains locally. The server emits the marker only for an actual stored versioned receipt, including exact replay. Legacy rows and disabled receipt mode do not emit it.
4. If the app restarts or loses a response, the import hub shows saved progress. Opening it sends nothing. An explicit resume replays the same saved body and key; when the server already committed, its existing receipt returns the original counters. A changed body under that key remains a conflict.
5. Switching accounts/signing out suspends sending and closes the owned transport. It retains the original account's queue and keys. Another account cannot list or send that queue. Signing back into the same account permits explicit continuation.
6. After 14 days, retained work requires an explicit review/continue action. Expiry never silently deletes financial input. Confirmed discard removes only remaining local batches, after confirmation, and refuses an active lease. Already committed server transactions remain.

No extra customer password or recovery-key file is introduced. This queue is local restart protection, distinct from opt-in encrypted account recovery. Losing the phone or its secure-store key can still lose the ability to decrypt unsent imports; retain the original source file. OTP sign-in recovers account access and committed server data, not unsent phone-only data.

## Storage and recovery contract

| Item | Implemented boundary |
| --- | --- |
| Payload encryption | AES-256-GCM envelope with random nonce, versioned header and authentication binding to account namespace, session, batch ordinal and import key. Bodies are canonical JSON. No source PDF, file password or access token is persisted in the queue. Existing parsed transaction fields are sensitive and encrypted; the rest of the existing SQLite database is not converted by this batch. |
| Key custody | Independent per-account random key through the existing secure-store custody primitive and cross-isolate provisioning lease. Not a login token, device identifier, server encryption key, SQLite key or receipt-file key. Missing/corrupt/unavailable custody blocks decryption and preserves ciphertext. Existing ciphertext also blocks replacement-key provisioning if secure-store metadata is lost. Keys never enter SQLite payloads, backups or reports. Real native custody remains a signed-device gate. |
| Space bounds | At most 64 batches/session, 64 KiB plaintext/batch, 65,569 bytes encrypted/batch, three active sessions/account and 8 MiB encrypted payload globally across accounts. Retained metadata is capped at 35 sessions/account and 1,000 globally; only terminal metadata older than 30 days is pruned, at most 100 sessions per new plan. Pending/leased data is never evicted to make room. These are logical payload/row caps, not a bound on the whole SQLite/WAL file or other app storage. |
| Execution bounds | One account lease, five-minute lease renewed every 20 seconds while active; own HTTP transport closes after 60 seconds and the runner awaits settlement. One request per pending batch per explicit run; it stops on the first failure. There is no automatic background retry loop. Server process admission remains two imports and one per account; cross-replica/provider fairness remains unfinished. Device clock changes may delay lease/expiry handling; they do not order financial mutations. |
| Account backups | Portable completeness checks count the new pending queue. Account recovery capture and fresh restore refuse pending batches; portable fresh restore also refuses them before writes. The three device-key-bound queue tables are excluded from account archives after draining. This prevents claiming an unrestorable pending import is backed up. Finish or explicitly discard pending work before creating/restoring a recovery copy. Existing account-recovery opt-in and quotas remain. |
| Migration | No new PostgreSQL migration in this batch. The prerequisite additive receipt migration remains required, preserves existing rows and is default off. Phone queue payloads are not PostgreSQL records; complete the queue before a device recovery transfer. Existing server identities/history/keys must still be preserved during the future PostgreSQL provider move. |

## Activation and rollback

`PANDAPAY_STATEMENT_IMPORT_CONTINUATION_ENABLED` is a Flutter compiler define, **false by default**; a server environment variable alone cannot enable a compiled app. No feature was enabled or deployment changed. The legacy import submit path remains the default and shares the same payload builder.

Before any rollout, accept the receipt migration/server behavior and enable `STATEMENT_IMPORT_RECEIPTS_ENABLED` through its existing gate. The release manifest must declare `statementImportReceipts:true` and `mobileImportContinuation:true`, match the reviewed build defines, and supply separate exact-candidate `statement_import_receipts_acceptance` and `mobile_import_continuation_acceptance` proofs. Local tests are not those acceptance proofs. The release checker rejects missing receipts or feature evidence.

After queue rollout, retain a compatible mobile build and server receipt reader/writer until pending queues have drained or users explicitly discard them. A build hiding the queue or an old server cannot be treated as a safe rollback merely by turning off flags. An unsupported/legacy response is retained for later replay, never acknowledged as complete. Do not replace original server keys or overwrite newer financial state with a pre-rollout snapshot.

## Decisions and deviations

- **Signals the server cannot measure are reported as `available:false`, never as zero:** sync error rate and migration failure rate. Sync outcomes and the migration report live on the phone and nothing uploads them; the server keeps no per-request outcome store, and the public and private admin APIs are separate processes, so in-memory counters would not help. Until the app reports them (or an owner supplies them from telemetry), `decision` stays `incomplete`, never `go`. Follow-up for the orchestrator: a small additive phone-reported counter (sync attempts and failures, migration outcome per profile) in WP-14/WP-16 plus a read in `sms_v2_release_metrics`.
- **Attestation counts are partial.** The verified or unverified decision is only stored on template submissions (`eligible`) and corrections (`shared_learning_eligible`); request-level counts exist only in logs. The metric reports those two.
- **Correction rate** is corrections created in the window divided by events whose `updated_at` is in the window. Events have no `created_at`, so a re-linked event counts again and the rate can read slightly low. Rule-stat correction rate (`rules.correctionRate`) is given alongside.
- **Windows:** rate counters are pruned after 2 days and per-profile rule stats after 48 hours, so `bundleChecks` and `rules.perCohort` cover at most 2 days whatever `days` is (`counterWindowDays`, `perCohortWindowDays`). The private admin session has a 5 s statement timeout; the function scans events and facts by date without a dedicated index, which is fine at tester scale and should be revisited before full rollout.
- **Gate exemptions:** `/ai/jobs/lease` and `/ai/jobs/:id/(heartbeat|result|retry|fail)` are the AI worker's calls (no app version), so they are never gated; the phone-facing `POST /ai/jobs` and `GET /ai/jobs/source/:key` are. `OPTIONS` passes. **Header-less callers count as old after the cutoff**, because no shipped app sends `X-App-Version` today (grep of `app/lib` finds none). The v2 app, and any flag-off release candidate kept for rollback, must send `X-App-Version` on these routes or be blocked once the cutoff passes. WP-17 should confirm this before setting a date.
- **Release script:** the production key is used only by the existing import script (signing happens server-side at mint). The golden command only loads signed-shape bundles, so the script signs a copy with a random throwaway key for the gate. It is for the first import; changes to existing rules go through the Rules page, because the import never rewrites a rule that already has version 1. The golden report is saved in the work folder; it is not attached to the minted bundles.
- **Fix outside the lane (3 lines):** `api/scripts/import_sms_v2_rules.js` failed on real tools-CLI output (`bundle.signature_required`, because `build` emits `signature: null` and WP-09 only tested with the signed contract fixture). It now adds a never-stored placeholder when the signature is null. Found by running the whole script against a scratch database.
- `api/src/sms_v2/index.js` was not edited: the route is registered through `registerPrivateTemplateRoutes`, which the admin routes file already calls.
- Suggest adding the new SQL test and `metrics_pg.test.js` to the list in `tests/admin_console_security/full_schema.test.js` (outside this lane, not edited).

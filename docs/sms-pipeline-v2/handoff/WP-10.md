# WP-10 AI per template

Implemented server flow on `codex/sms-v2-wp10-templates`, based on `e28210f` with CCR-001 and WP-13 security available.

## Behavior

- `POST /sms/v2/unknown-templates` validates the frozen request, checks redaction again, requires current purpose-specific consent and calls the attestation and rate hooks. PostgreSQL repeats privacy checks and enforces the profile's 50-item daily cap in one transaction.
- Unverified monitor submissions are stored as held. Only verified, consented submissions count toward shared frequency and can authorize AI work. The first verified sample replaces an earlier held sample. A sender conflict for the same hash is rejected. Hashes come from the phone's original template identity because redaction changes printed values.
- One queue row exists per hash. Private workers claim popular templates first, then recent live templates, then older ones. A lease prevents concurrent calls. An interrupted provider call becomes failed after its lease expires, avoiding an unbounded retry bill.
- Calls reserve shared PostgreSQL RPM and TPM capacity. The default RPM is 60. TPM and model are required configuration. Output-token limit and optional per-million token prices are configurable. Cost records retain model, input/output/total tokens and latency, including repair calls. Missing pricing appears explicitly in metrics.
- The prompt includes redacted text, brand, frozen schema data and up to five public rule summaries. It excludes profile IDs, source SMS and example bodies from existing rules. Gemini's `generateContent` JSON mode is used with a bounded response and timeout. Tests use a mocked provider.
- Draft validation checks the Rule schema, metadata, exact template and sender scope, a hash-derived rule ID, regex dialect, named groups, populated sample captures, emitted attrs, examples and conflicting family words. Validation runs in a disposable worker thread with a timeout. Two distinct synthetic positive examples and two negatives are required. The worker permits one repair pass.
- Sync returns provisional rules only for templates the account submitted. Revisions are allocated under a transaction advisory lock so cursor advancement follows commit ordering. Later submissions of an already drafted template still receive it. CCR-001's optional `aiResults[].rule` is used.
- Consent revocation removes submitter access in the consent transaction. Profile deletion removes its association and orphan redacted templates. Cost records remain as platform accounting. Queued work loses its lease when no eligible submitter remains.
- Private admin routes list templates, show daily AI usage and copy ready provisional rules into ordinary WP-09 drafts. That explicit promotion removes the template-hash restriction. Reviewed publication still uses the golden gate.

## Worker operation

The worker runs as the `sms-v2-template-worker` service in the private admin profile (`deploy/admin/compose.private.yml`, `node src/sms_v2/jobs/template_worker_main.js`), only on the private admin host. `node api/scripts/run_sms_v2_templates.js` (add `--once` for a single iteration) still works from an operator checkout. Configure `ADMIN_API_DATABASE_URL`, `SMS_V2_JOB_ADMIN_ID`, `GEMINI_API_KEY` (paid tier only), `SMS_V2_AI_MODEL`, `SMS_V2_AI_TPM`, `SMS_V2_AI_INPUT_USD_PER_MILLION` and `SMS_V2_AI_OUTPUT_USD_PER_MILLION`. The active actor needs `learning.publish`. Optional settings are `SMS_V2_AI_RPM` and `SMS_V2_AI_MAX_OUTPUT_TOKENS`. See `deploy/admin/RUNBOOK.md`.

The prompt carries a placeholder legend (`SMS_PLACEHOLDERS`) and India SMS domain rules (`SMS_DOMAIN_RULES`) in `api/src/sms_v2/template_worker.js`, rewritten from the deleted per-message prompt in v2 fact vocabulary.

Provider request fields follow the [official Gemini generateContent API](https://aistudio.google.com/api-reference/generate-content).

## Dry run on the owner's layouts (Phase 6b, Task 6b.5)

`api/scripts/dry_run_sms_v2_templates.js` (dev only, not in the image) drafts rules for stored layouts with the worker's prompt and checks, and writes nothing to the database. It reads layouts and example rules in one read-only transaction as the owner (`learning.read`), closes the database, then calls the provider. The output file holds redacted layouts and drafts and must be outside the repository (the script refuses otherwise); the console shows only sender, status, valid and error codes.

1. On the rig build, the owner turns on Settings → Privacy & permissions → "Help PandaPay read new bank messages" and leaves the app open after a history import. The rig has no App Check, so layouts arrive as `held`; the script reads every status. The cap is 50 layouts per account per day.
2. Rehearse without a key or any AI call: `ADMIN_API_DATABASE_URL=<rig> SMS_V2_JOB_ADMIN_ID=<owner admin_users.id> node api/scripts/dry_run_sms_v2_templates.js --provider fake --limit 50 --out <scratch dir>/ai-dry-run.json`. Every draft comes back invalid; this checks the database, permissions and output.
3. Run with a paid key: `ADMIN_API_DATABASE_URL=<rig> SMS_V2_JOB_ADMIN_ID=<owner admin_users.id> GEMINI_API_KEY=… SMS_V2_AI_MODEL=… SMS_V2_AI_TPM=… SMS_V2_AI_INPUT_USD_PER_MILLION=… SMS_V2_AI_OUTPUT_USD_PER_MILLION=… node api/scripts/dry_run_sms_v2_templates.js --limit 50 --out <scratch dir>/ai-dry-run.json`. The summary has token totals and, with prices set, the estimated cost.
4. The owner reads each draft in the output file. Record below: layouts tried, drafts valid, drafts the owner would publish without edits, and the common failure codes. Suggested bar before friends opt in: at least 7 of 10 valid drafts need no edit. Otherwise adjust `SMS_DOMAIN_RULES` and run again.

Offline check without a database: `--layouts <file.json>` with an array of `{senderBrand, redactedBody}` (redacted text only; unredacted bodies are refused before any call).

## Evaluation before a prompt or model change (learning loop, Task B2)

Run this before changing `SMS_DOMAIN_RULES`, the prompt or the model (every attempt records `prompt_version`, currently `tpl-2026-11-16`, so results can be compared). `--eval` takes each layout whose AI draft the admin approved with "Create draft" (`admin_decision = 'approved'`), drafts it again with the current prompt, and prints "N of M approved drafts reproduced". A draft is the same when it emits the same fact types with the same amount roles. It reads in one read-only transaction and writes nothing back:

```
ADMIN_API_DATABASE_URL=<rig> SMS_V2_JOB_ADMIN_ID=<owner admin_users.id> GEMINI_API_KEY=… SMS_V2_AI_MODEL=… SMS_V2_AI_TPM=… \
  node api/scripts/dry_run_sms_v2_templates.js --eval --limit 50 --out <scratch dir>/ai-eval.json
```

Offline: `--eval --layouts <file.json>` with rows `{senderBrand, redactedBody, approvedDraft}`; `--provider fake` rehearses without a key (it reproduces nothing). Do not switch the prompt or model if the count drops without a reason you can explain.

# WP-05 handoff: Event linker

Branch `sms-v2/wp-05-linker` (from `sms-v2/main`). No contract file, rule file or Gmail file was touched.

## What was built

**Domain: `packages/pandapay_domain/lib/src/sms_v2/linker/`** (exported by one added line in `lib/sms_v2.dart`, as WP-02 and WP-04 did)

- `rule_driven_linker.dart`: `RuleDrivenLinker implements EventLinker`.
  - `RuleDrivenLinker.fromBundle(bundle)` reads the bundle's `senders` (which wallets are `walletSpendVisibility: partial`) and `counterpartyPurposes` (which top-up payee goes to which wallet). An optional `clock` decides when a receipt's window has passed.
  - `link(incoming, context, rules)`: facts in fixed order (`occurredAt ?? observedAt`, then `factId`); only `movement`, `hold`, `mandate` take part. Per fact: (1) pair rules by priority, joining the single other leg found (open or one-leg events first, then unlinked facts); 2+ candidates give an `ambiguous` event and a `ReviewItem`; (2) `LINK-DUP-NOTIFY`; (3) the first rule that lets the leg stand alone (`singleLeg`); (4) purpose typing (Build 4 table). Receipts (`evidenceOnly`) never make an event; `LINK-RECEIPT` joins them as `duplicate_notice`.
  - `expire(now, context, rules)`: stale `awaiting_leg` events become `complete`; with a `RuleLinkContext`, receipts past their window with no payment become review items.
  - `linkRuleKindOf(rule)`: what each rule means to the code, from its event type and leg roles, never its id.
- `link_context.dart`: `RuleLinkContext extends LinkContext` adds `instrumentIdByFactId` and `knownEvents` (see Deviations 1).
- `golden_support.dart`: `linkForGolden(facts, instruments, bundle)`, plain JSON in and out, for the golden tool.

**App: `app/lib/features/sms_v2/storage/event_store.dart`**: `EventStore(db, namespace:)` on `v2_events`: `upsert` (legs only grow; a `user_confirmed` row changes only with `fromUser: true`), `upsertAll`, `get`, `findByFactId`/`findByFactIds` (SQLite `json_each` over legs), `listOpen({from, to})`, `listSince(from)` (the `knownEvents` for a context), `dirty`, `markDirty`, `markClean`, `count`. Every query is namespace-scoped.

**Golden wiring: `tools/sms_rules_cli/lib/golden/adapters.dart`**: WP-04's `_RegistryInstrumentStage` patch (its handoff item 2) plus a `_RuleLinkerStage` over `linkForGolden`. About 45 lines, no other CLI file changed.

## Behaviour by case

| Case | Result |
| --- | --- |
| Card bill, bank debit + card receipt (either order, 72 h, equal amount, debit's destination mask must match the card) | `card_bill_payment [debit_leg, credit_leg]` |
| CHEQ / CRED / BBPS debit (`card_payment`, counterparty own), no receipt | `card_bill_payment [debit_leg]` (WP-06 sends it to `ownUnresolved: credit_card`) |
| Wallet top-up debit + wallet credit (48 h; the payee's wallet must match the credited wallet) | `wallet_topup [debit_leg, credit_leg]`; wallet purchases stay `purchase` |
| Amazon Pay top-up (payee maps to a `partial` wallet) | `purchase [debit_leg]` (also when joined with a credit); Amazon balance payments and refunds: no event, no review |
| IPO hold placed | `ipo_application [hold_placed]`, `awaiting_leg`, `amountMinor` 0 |
| + release / + allotment debit / partial (debit + later release) | joins as `hold_released` / `debit_leg`; `complete` once debit + released ≥ held; `amountMinor` = debit only |
| UPI one-time IPO mandate (hold + mandate in one message) | the mandate joins the IPO event as `original`; never a subscription |
| Mandate then debit (`mandateRef` = mandate reference, or counterparty = merchant; active, ≤ ceiling) | `subscription_charge [charge, original]`; anchor is the charge, the mandate is shared by every charge |
| Debit with `mandateRef`, no mandate seen | `subscription_charge [charge]` |
| Refund (same instrument, counterparty compatible, ≤ purchase minus earlier refunds, 120 days) | `refund [reversal, original]`; the purchase keeps its own event |
| Debit to own account (counterparty `own`, or destination mask = an own bank account) + credit | `own_transfer [debit_leg, credit_leg]`; a lone own debit is `own_transfer`; a credit seen first is upgraded when its debit arrives |
| Bank debit + UPI app notice (10 min, same amount, same account when both known) | `<type> [debit_leg, duplicate_notice]`; the notice naming the account is the money leg |
| Biller / app receipt (`evidenceOnly`) | joins the debit as `duplicate_notice`; none in 3 days: review "We saw a receipt from <biller> for Rs X but no payment. Add it?" |
| Broker payout (`movement` credit, purpose `investment`) | `investment_withdrawal [credit_leg]` |

## Evidence for the done criteria

- **Zero double counts across the golden scenarios.** Linker level: no fact is a money leg (`debit_leg`, `credit_leg`, `charge`, `reversal`) of two events and no receipt is ever a money leg: 0 across all 15 scenarios (`golden_linker_test.dart`) and across the 20,000-fact benchmark. The golden tool's own `doubleCounts` needs the projector (WP-06) and is still `not_available`.
- **At least 98% of expected pairs linked: not met on the golden set (7 of 8, 87.5%), because of rules, not the linker.** The missing pair is `duplicate_notice_bank_and_upi_app`: the HDFC debit falls to the last-resort rule (`chaipoint` contains `ipo`, a `rejectAny` substring) and the Google Pay notice matches no rule. Request filed: `requests/WP-05-dup-notice-rules.md`. With the facts those rules should produce, the linker gives the expected pair (unit test `LINK-DUP-NOTIFY joins a bank debit and a UPI app notice`). With both fixes the golden set is 8/8.
- **Every probe scenario gives the expected events**: card bill pair, card bill via CHEQ, wallet top-up then spend, Amazon Pay top-up, IPO block then release, IPO block then allotment all pass (golden and `golden_linker_test.dart`).
- **Performance**: 20,000 mixed facts in about 0.2 s (`benchmark_test.dart`, gate 5 s). Lookups use buckets by amount, time-sorted indexes with window range queries, and name/reference indexes for mandates and refunds; there is no all-pairs comparison. Single-family stress runs (all refunds, all IPOs, all mandates) stay under 1.2 s.
- **Tests** (`test/sms_v2/linker/linker_test.dart`, 61): each link rule positive and negative; legs in either order; leg after the window; partial IPO allotment (incremental, one message per call); refund larger than the purchase; duplicate notice across a bank and a UPI app; ambiguity creates a review item (and a shared reference breaks the tie); idempotent re-run over stored events; one-message-at-a-time equals one batch and legs never shrink; `user_confirmed` untouched; expiry; purpose typing for every purpose.

## Deviations and decisions to confirm

1. **`instrumentIdByFactId` is not on the frozen `LinkContext`.** WP-05.md says the context carries it; the WP-01 class has only facts, open events and instruments. `RuleLinkContext` (a subclass, no contract change) adds it plus `knownEvents`: every stored event touching the recent facts. Without `knownEvents` the linker cannot know whether a recent fact is already joined in a `complete` event, so with a plain `LinkContext` it only joins recent facts that never make an event of their own (receipts, mandates, refund originals); a credit seen in an earlier batch is then not upgraded by its later debit. The pipeline (WP-14) should pass a `RuleLinkContext` built with `EventStore.listOpen()` and `listSince(now - 120 days)`. With no `instrumentIdByFactId` entry, a mention is matched to a unique known instrument by issuer, kind and mask.
2. **One-leg events stay joinable.** "First in open events" read literally would leave a card receipt seen before its bank debit as two events, and a transfer credit seen first as `p2p_in` income plus an `own_transfer`. A one-leg event made by the same rule, or by purpose typing, is a candidate too (never a `user_confirmed` or `ambiguous` one). Its anchor and id do not change; it gains the leg and the rule's type.
3. **Which lone legs use `singleLeg`**: card bill and wallet top-up (either leg), IPO (`hold_placed` only), own transfer (only when the leg itself is own). Refund, mandate charge, receipt and duplicate rules never stand alone; purpose typing gives those facts their one-leg type, so a purchase never becomes a one-leg "refund".
4. **Rule parameters read as the 03d handoff says**: tolerance 100 means "up to" (refund ≤ purchase, debit or release ≤ held, charge ≤ ceiling); `LINK-RECEIPT` and `LINK-DUP-NOTIFY` keep the anchor debit's type (an `unknown` anchor takes the notice's type).
5. **Time distance** is the smaller of the printed-time and received-time distances, so a printed date with no time (IST midnight) does not push two messages a minute apart outside a 10-minute window. Index ranges are widened by 2 days for the same reason.
6. **Guards the rules cannot express**: a mandate charge needs `mandateRef` or a counterparty name and a purchase-like purpose (`purchase`, `unknown`, `bill_payment`, `p2p`); one-time, IPO, SIP and loan mandates are skipped; revoked, paused or expired mandates are inactive. IPO legs must share the account and an issue name when both are printed. Duplicate notices need the same account when both are known, a shared reference when both carry one, and are never two facts from the same rule on the same account without a shared reference (two real payments). Two facts from one message never pair.
7. **A refund naming no merchant links only on the exact amount.** Matching it to "any larger purchase on the card" made nearly every such refund ambiguous on a busy card. A partial refund without a merchant stays a one-leg refund (no review).
8. **IPO `amountMinor` is 0 until the debit arrives** (the held amount is never the investment). `occurredAt` and `amountMinor` come from the earliest money leg (`debit_leg`, `credit_leg`, `charge`, `reversal`); `original` and `duplicate_notice` legs never set them. Confidence is the lowest leg fact's.
9. **Review items** are `ReviewKind.event` with `payload.reviewId` (`link:ambiguous:<factId>`, `link:receipt:<factId>`), `reason` (`ambiguous_link`, `receipt_without_payment`, `missing_leg`), and the candidates. A receipt with several matching debits gets an `ambiguous_link` review and no event.
10. **Golden adapters** (`adapters.dart`, WP-00's file) were edited as the brief asked; the instruments stage is WP-04's tested patch.

- `compiled_bundle.dart`: `CompiledBundle.compile(bundle)`: refuses a bundle whose `minEngineVersion` is newer than `smsEngineVersion` (`2.0.0`), validates it, builds regexes once, indexes by brand (merged with generic rules), sorts. Throws `BundleRefusedException`.
- `rule_engine.dart`: `RuleEngine implements SmsInterpreter`. ## Decisions to confirm (spec was silent)

1. **Unknown reason.** `InterpretResult` has no reason field and is frozen, so the reason (`no_rule_matched`, `rule_emitted_invalid`, `bundle_refused`, `engine_error`) is in `EngineOutcome` and `EngineStats`.
2. **Ordering.** Priority descending, then brand rules before generic rules, then id. (Contracts say "priority, then id"; "brand before generic" only matters at equal priority.)
3. **requireAll / rejectAny** are case-insensitive substring checks on the whole body.
4. **Mask overlapping a date** drops the mask (instrument keeps kind and issuer) and counts `maskDateOverlaps`; it does not make the whole emit invalid.
5. **maskLength** is the number of printed digits unless the emit gives `maskLengthFrom`. A capture longer than 6 digits keeps the last 4 as `maskDigits`. Consumers (WP-04) should not treat a 4-digit `maskLength` as the full card length.
6. **Counterparty purposes** match on vpa OR name (case-insensitive), apply to debits only, and set `counterparty.kind = own` for `wallet_topup` / `card_payment`.
7. **References**: `ref_<key>` groups attach to movement, attempt, hold, mandate and bill_due facts; `emit.references` (key to group name) attaches to any fact.
8. **Attrs** accept `{sameAs, field?}` (`field` may be `occurredAt`, which falls back to `observedAt`) and `{from, formats?, transforms?}` (typed by key: `dueDate`/`statementDate` as IST date, `asOf`/`dueAt`/`expiresAt` as UTC instant, `previousMinor` as paise).
9. **Rule statuses**: only `active` and `provisional` rules run. Templates hashes come from `smsTemplateBrand` + `smsSkeleton` (WP-00), the same as `cluster`.
10. **Unsigned bundles in tooling.** The contract requires a signature above version 0, so `build`/`lint`/`sign-dev` attach a placeholder signature in memory only; written files have `signature: null` until `sign-dev` or the server signs.
11. **Rules folder layout** read by `build`/`lint`: `senders/*.json`, `ignore_rules.json`, `counterparty_purposes.json`, `link_rules.json`, `category_rules.json`, `merchant_aliases.json`, optional `meta.json` (bundleVersion, createdAt, ...), and every other `*.json` as a rules array. WP-03 should follow this.

## Deviations

- Added one export line to `packages/pandapay_domain/lib/sms_v2.dart` and `cryptography` to the CLI `pubspec.yaml` (for Ed25519 in `sign-dev`).
- Edited `tools/sms_rules_cli/lib/golden/adapters.dart` (WP-00's file): `loadDefaultAdapters` now builds the interpreter stage from `--bundle` (the file's own TODO said the orchestrator would). Other stages are still `not_available`.
- `fetch-baseline` uses `GET /admin/sms/v2/bundles/latest` (override with `--path`; base URL from `--api-url` or `SMS_API_URL`). Contracts list no download route, so WP-09 must provide this one or the default changes. Not exercised against a server.
- CI does not yet run `node tools/sms_rules_cli/test/regex_parity.mjs`: the workflow file is outside this package's paths. The same check also runs inside `dart test` in `tools/sms_rules_cli` (skipped if `node` is missing). The orchestrator should add a CI step.

## Results

- Benchmark on a dev laptop (JIT): compile 1,000 rules about 40 ms; 10,000 messages about 600 ms.
- `golden` over the 82 seed cases with the sample bundle runs and reports metrics (the sample has one rule, so recall is low by design); WP-03 supplies the real rules.

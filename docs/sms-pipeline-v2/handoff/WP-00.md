## What the orchestrator must do after WP-01 merges (the `golden` binding)

`golden` runs today against `tools/sms_rules_cli/lib/golden/adapters.dart`, a local interface that uses plain JSON maps (Fact, Instrument, Event, LedgerEntry shapes from contracts.md). Every stage is `not_available` until wired. To bind:

1. Implement `loadDefaultAdapters({bundlePath})` in `adapters.dart` so it returns, from the `--bundle` file:
   - `interpreter` (`InterpreterStage.interpret(GoldenMessage) -> InterpretedMessage{facts, unknown}`) wrapping `SmsInterpreter`; facts via `toJson()`; `unknown: true` when no rule matched.
   - `instruments` (`resolve(facts, knownInstruments) -> InstrumentResolution{instruments, facts}`) wrapping `InstrumentResolver`.
   - `linker` (`link(facts, instruments) -> events`) wrapping `EventLinker`. Events need `eventId`, `type`, `legs: [{factId, role}]`.
   - `projector` (`project(...) -> ledger entries`, `totals(entries, from, to) -> LedgerTotals`) wrapping `LedgerProjector`. `totals` must call the ledger package's own totals function.
   - `categories` (`categorize(entries)` sets `category`) wrapping `CategoryResolver`.
2. Rename or alias fields if WP-01's JSON differs from the names used here (`factType`, `attrs`, `amounts[{role,minor,unit}]`, `instrument{kind,issuerSlug,maskDigits}`, `legs[{factId, role}]`).
3. Run `dart run bin/sms_rules.dart golden --bundle ../../app/assets/sms_rules/baseline_bundle.json --baseline ../sms_golden/reports/latest.json`, then recommit `reports/latest.json` (currently an all-`not_available` report, so the baseline comparison passes trivially).
4. Add the `golden` step to CI when WP-03 lands (per Test and release).

Behaviour already implemented and tested: loading, partial matching, per-dimension scoring (kind, amount, instrument), weights by `weight`, rupee weighting, per-family and per-brand slices, scenario pipeline, gates (`--profile m1|release|none`), `--baseline` (any worse metric exits 1; `askRate` and `doubleCounts` are lower-is-better), `--require-stages`, `report.json` and `report.md`.

## Decisions and assumptions to review

- **Cases pool facts.** A case with several messages pools their facts before matching. Each expected fact is matched to the actual fact of the same `factType` that matches most dimensions; kind, amount and instrument are scored separately.
- **Metric definitions** (see `scorer.dart`): ignore precision counts messages the system ignored (only `info` facts, not unknown); ask rate is unknown results over financial case weight (cases only; scenarios do not add review items); `doubleCounts` is the number of scenarios whose actual spend, income, investment or count exceeds the expected value; `pairsLinked` counts expected events with 2 or more legs. Extra reported metrics (not gated): `eventKindByAmount`, `amountRoleByAmount`, `instrumentByAmount`, `scenarioEvents`, `scenarioInstruments`.
- **Case format additions** (all optional): `family` (otherwise guessed from the body by the ported `analyze.py` family list), `note`, `origin`.
- **Scenario assumptions that WP-05 and WP-06 should confirm** (changes go through a CCR):
  - Event leg roles: refund event = `[original, reversal]`; mandate charge = `[original, charge]` (the mandate fact is the `original`); IPO block then allotment = `[hold_placed, debit_leg]`; duplicate notice = `[debit_leg, duplicate_notice]`; single-leg events use `debit_leg` or `credit_leg`.
  - A refund keeps its purchase as its own event, so refund scenario totals are spend 0 and count 2 (refund counts as a transaction and nets the category). A cheque debit is typed `purchase`. Points scenario expects only the purchase event. An Amazon Pay balance payment is an `evidenceOnly` movement and creates no event; the top-up is the spend.
- **Contract gaps found while converting:** `corpus:autopay_failed` has no printed amount but `attempt` requires a `posted` or `scheduled` amount; `corpus:kotak_settlement` and several `local:` attempts omit amounts for the same reason. `outstanding_reminder` is expected as `bill_due` (due_total) although it says "outstanding".
- **Merchant names are not scored** in cases (only partial `counterparty.kind` where the contract fixes it).
- **Probe cases location:** converted into `cases/<BRAND>/<hash>.json` like every other case, with ids `probe:*`, `corpus:*`, `local:*`. The loader reads every folder under `cases/`, so do not also copy `probe_cases.json` into `cases/_probe/`: the loader would read both sets.

## Redaction and clustering

- `redactSms` (pure Dart): phones, URLs and emails to `<PHONE>`, `<URL>`, `<EMAIL>`; UPI IDs kept only when every part is a known word or catalogue merchant; digit runs of 4+ and masks to synthetic digits of the same length (each digit differs from the original, consistent inside a message); amounts keep their format but change value; dates keep their format and shift by one per-run offset (also applied to `observedAt`); names become `<PARTY>`: names after trigger words, plus a safety net for any capitalised word that is not in the bundled vocabulary or merchant catalogue (a missing word is redacted, never leaked). Default salt is random per run.
- `cluster`: brand + skeleton, then any word seen in fewer than 5 messages becomes `<W>`; `templateHash` is the full sha256 hex.
- Known limit: redaction is conservative on capitalised words, so rare wording in real exports may become `<PARTY>`. A person must still review redacted cases before they move into `cases/`.

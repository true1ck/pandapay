## Resolver rules, as built

First hit wins; every tier needs the rule's `senders` (`*` or the normalised sender brand) and `context` to be satisfied.

| Row | Source | Confidence | Selection inside the tier |
| --- | --- | --- | --- |
| 1 | `userRules` (source `user`) | 1.0 | satisfied contextual rule, then sender-specific, then longer match, then higher priority (the adapter sets priority to `updated_at`, so the newest choice wins) |
| 2 | bundle rules with source `shared` | 0.95 | priority, then longer match |
| 3 | bundle rules with source `catalogue` | 0.9 when the rule key is the whole merchant key, else 0.8 | longest match (token count), then priority |
| 4 | `confirmedHistory[merchantKey]` | 0.85 | n/a |
| 5 | `ResolverInput.aiSuggestion` (must be in the taxonomy and not `other`) | 0.6 | n/a |
| 6 | `other`, source `default` | 0 | n/a |

- **Matching** is on the merchant key only. `contextTokens` only satisfy a rule's `context`; they never match a merchant, so a brand in a footer cannot categorise a spend.
- **Context** is satisfied when any context token of the rule is a token of the merchant key or one of `input.contextTokens`.
- **Match kinds:** `token` is a contiguous token span, `exact` is the whole key, `prefix` and `contains` are plain string tests (the catalogue uses only `token` and `exact`).
- **Slugs** are checked against the registry in every tier. A rule or history entry with an unknown slug is skipped, and aliases resolve to the current slug.
- **`decide(eventType, input, linkedPurchase)`**: returns null unless the type is `purchase`, `subscription_charge`, `fee`, `emi`, `bill_payment`, `atm_withdrawal`, `p2p_out` or `refund`. A refund returns `linkedPurchase` as is, or resolves on its own counterparty. `p2p_out` consults only user rules (keyed by the merchant key or `personRuleKey`: UPI ID, else name) and otherwise gives `other`/`default`.
- **`ruleId`** is `<tier>:<KEY>[+<context tokens>]` (for example `catalogue:SWIGGY INSTAMART`, `history_confirmed:KIRANA`); the AI and default decisions have none.
- Compiled rules are cached per rule-list instance, so pass the same list for a whole batch.

## `merchantKey`

Upper-case; every character outside `A-Z 0-9 &` becomes a space (`MCDONALD'S` is `MCDONALD S`, `APPLE.COM/BILL` is `APPLE COM BILL`); trailing `PVT`, `PRIVATE`, `LTD`, `LIMITED`, `LLP`, `INC`, `LLC`, `PLC` and `(P)` before them are stripped (never the last token). Alias keys and targets go through the same normalisation. An alias is tried on the whole key, before and after the suffix strip. A UPI ID is tried against the alias table (full ID, then local part), then its readable local part is used (tokens with 4 or more digits and gateway words like `RZP`, `PAYU`, `QR` dropped; a number gives no key). A `person` or `own` counterparty gets no key. Name wins over UPI ID when it yields a key.

## WP-03d assumptions: confirmed against the files

Checked by `rules_files_test.dart` over `rules/sms/v2/category_rules.json` (411) and `merchant_aliases.json` (78):

- **Whole tokens:** every rule matches its own key and gets its category and the `catalogue` source; each also matches inside a longer name (`<KEY> KORAMANGALA`); a key never matches inside another word (`X<KEY>Y`). `KUBER`, `SPARK`, `SHELLY`, `SUBER` give nothing.
- **Exact-only:** `OLA` and `VI` match only as the whole key.
- **Aliases on the whole key:** all 78 map their alias to the target, and the alias resolves like the target. `AMAZON PAY IN KARNATAKA` is not aliased (it still resolves `online` through the `AMAZON` token rule).
- **Context:** `INDIGO` needs a context token; each of `AIRLINES`, `AIRLINE`, `AVIATION`, `FLIGHT`, `6E` works, whether it is in the merchant key or in `contextTokens`. `INDIGO PAINTS` gives `other`.
- **Rule keys** are already in normal form (including `H&M`, `L&T FINANCE`) and carry no legal suffix.
- **Seven aliases have no category on their target** (`PAYTM`, `CRED`, `GROWW`, `UPSTOX`, `ZERODHA`): by 03d's design (ambiguous or investments). They only normalise the key. The test pins this set.
- **Collisions:** all audit collisions pass. UBER EATS is dining, SWIGGY INSTAMART is groceries, AMAZON PAY IN and AMZN MKTP IN are online, AMAZON PAY WALLET is wallet, INDIGO needs context.
- **Priorities** play no part in tier 3 except as a tie-break after length, as 03d described. No change is needed in the rules files and none was requested.

## Deviations and decisions to confirm

1. **New library `lib/sms_v2_category.dart`** (outside the owned `category/` folder) instead of editing `lib/sms_v2.dart`, which WP-07 has no touch point for. It follows the precedent of `sms_v2_template.dart`. If the orchestrator prefers one export, add `export 'src/sms_v2/category/...'` lines to `sms_v2.dart` and delete the new file.
2. **`ResolverInput`** subclasses `CategoryInput` to carry `aiSuggestion` (row 5), because the frozen `CategoryInput` has no such field. A plain `CategoryInput` works and simply has no AI tier.
3. **Aliases are a constructor argument** of `DefaultCategoryResolver` (`bundle.merchantAliases`), not part of `CategoryInput`, for the same reason. Build one resolver per bundle.
4. **The contract has no `admin` category source**, only `shared`; tier 2 therefore reads `shared`. Bundle rules with `user`, `mcc`, `history_confirmed`, `ai` or `default` as source are ignored.
5. **MCC** is not used: WP-07's table has no MCC row. `CategoryInput.mcc` is accepted and ignored. `CategorySource.mcc` stays available if a later package wants a row between 4 and 5.
6. **`categoryIdForSlug(slug, idBySlug)`** takes the slug-to-id map from the category catalogue the app already loads (`SpendCategory.slug` and `id` from `GET /categories`), because ids are database UUIDs and not constants. It follows deprecated aliases and returns null when the catalogue lacks the row.
7. **Old layout rules widen.** The old pipeline stores user corrections as `CTX|MERCHANT|SENDER|TEMPLATE` (one message layout). v2 matches on the merchant only, so `UserCategoryRules.load()` reads these as "this merchant from this sender" and drops the layout. A user who corrected one layout of a merchant now gets it for that merchant and sender. Only rows with `source = 'user'` are read; unknown slugs are skipped.
8. **No schema change.** Contextual or sender-limited choices written by `saveChoice` are encoded in the existing `pattern` column as `V2|KEY|SENDERS|CONTEXT`; a plain choice is just the key, as before. The old reader (`loadRulesSync`) sees the V2 rows as unknown patterns and ignores them.
9. **"A correction through WP-12" is a hook, not wired.** WP-12 does not exist yet, so `saveChoice` calls an optional `CategoryChoiceSink` (merchant key, slug, sender, context). WP-12's `CorrectionsService` should pass its sink when it builds `UserCategoryRules`.
10. **Golden `categories` stage not wired** (WP-07.md lists no touch point in `tools/sms_rules_cli`). Wrapper for the orchestrator, in `adapters.dart`'s `loadDefaultAdapters`: a `CategoryStage` whose `categorize(entries)` sets `category`, `categorySource` and `confidence` on each entry that is a spend, by calling `DefaultCategoryResolver(aliases: bundle.merchantAliases).decide(eventType: <event type of entry.eventId>, input: CategoryInput(counterparty: <counterparty of the anchor fact>, senderBrand: ..., bundleRules: bundle.categoryRules))`. It needs the event type and the counterparty of each entry's event, which the entry JSON does not carry, so it belongs next to the projector wiring.
11. **Request filed:** `requests/WP-07-golden-category-slug.md` (`food_dining` in `refund_after_purchase.json` should be `dining`).

## Follow-ups for other packages

- **WP-06 (projector):** set the ledger entry's `to.external` to the same key the resolver used: `MerchantKeyer.keyFor(counterparty)`, or `personRuleKey` for a person. `confirmedHistoryFromLedger` looks history up by that key. Call `decide(...)` per event and store `slug` and `source` on the entry; keep `category` null for events `decide` returns null for. For a refund, pass the linked purchase's decision.
- **WP-06 / WP-12:** when a user changes a category, write the new entry with `categorySource: user` (and later entries from history with `history_confirmed`), so the choice feeds row 4.
- **WP-04 / orchestrator:** a user rule saved under a key that a later bundle re-aliases stops matching (the rule is keyed on the old canonical key). Rare; saving the choice again fixes it.
- **Person names:** the resolver relies on `counterparty.kind == person` to refuse a key. A VPA like `mohan.kumar@oksbi` with kind `unknown` yields `MOHAN KUMAR`, which matches no catalogue rule but could be used as a history key. Rules should set `kind: person` for p2p.

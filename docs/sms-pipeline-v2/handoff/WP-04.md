# WP-04 handoff: Instrument registry and detection

Branch `sms-v2/wp-04-instruments` (from `sms-v2/main`). No contract file was touched.

## What was built

**Domain: `packages/pandapay_domain/lib/src/sms_v2/instruments/`** (exported by one added line in `lib/sms_v2.dart`)

- `instrument_resolver.dart`: `DefaultInstrumentResolver implements InstrumentResolver`.
  - `resolveDetailed(mention, known, {profileId, observedAt, senderBrand})` returns a sealed `InstrumentOutcome`: `InstrumentResolved(resolution)`, `InstrumentReviewNeeded(reason, candidates)` or `InstrumentNotCreated(reason)`.
  - `resolve(...)` is the frozen interface method. It returns the resolution, or throws `InstrumentNotResolvedException(outcome)` (the interface can return nothing else).
  - Matching order is exactly the contract's: exact key, then issuer + mask when the mention has no kind, then issuer + kind when it has no mask, then create. Ambiguity (2 or more) creates nothing and returns review `ambiguous`. A `rejected` match returns review `rejected`. Issuer + mask with no kind and no match returns review `kindUnknown`.
  - Identity never uses `maskLength` or the sender id. A created instrument stores `maskLength` only when it is longer than the mask (the engine's value is the printed digit count).
  - New instruments: uuid v4, `detected`, name `HDFC credit card ••5678`, sender brand and product name as aliases, `evidenceCount` 0 (the caller then applies the fact).
  - Creation rules: needs an issuer; a mask (2 to 6 digits), or, for `wallet`, `broker`, `pay_later`, no mask (one per issuer and kind). A mask-less card or account matches only a single existing one.
  - UPI-app senders (`SBIUPI`, `PHONPE`, `GPAY`, `BHIM*`, any brand containing `UPI`) never create a `bank_account` (`upiAppMask`); they may still match an existing one. Counterparty digits are not mentions, so they never reach the resolver.
  - Wallets with `walletSpendVisibility: partial` (Amazon Pay) never become instruments (`partialWallet`). `DefaultInstrumentResolver.fromBundle(bundle)` reads that from `bundle.senders`.
- `apply_fact.dart`: `applyFactToInstrument(Instrument, Fact, {senderBrand})` (pure) and `applyFact(...)`, which also carries `limitHistory`.
  - `balance_snapshot`: `available_balance` or `available_credit` update `available*`, `points_balance` updates `points*`, only when `asOf` is strictly newer than the stored time. `outstanding` is not stored.
  - `limit_change`: updates the credit limit with source `sms` unless the stored source is `user`; ignores a change older than the stored limit; keeps the last 5 changes (`LimitChangeRecord`, oldest first); no entry when the value is unchanged.
  - `instrument_hint`: adds `instrument.productName` (case-insensitive, once) and, for `linked_upi`, `counterparty.vpa` (lower case, once).
  - Every fact: `lastSeenAt` moves forward, `firstSeenAt` back, `evidenceCount` + 1.
- `golden_support.dart`: `resolveInstrumentsForGolden(facts, knownInstruments, {bundle})`, plain JSON in and out, for the golden tool's instruments stage (see below).

**App: `app/lib/features/sms_v2/`**

- `storage/instrument_store.dart`: `InstrumentStore(db, namespace:)` on `v2_instruments`. `upsert` (by id, then identity key), `get`, `findByKey`, `findByUserCardId`, `list`/`listByStatus`/`listByKind`, `dirty`, `markDirty`, `markClean`, `limitHistory`, `count`. Every query is scoped to the namespace.
- `instruments/instrument_seeder.dart`: `InstrumentSeeder.seed(cards:, issuerSlugOf:, bankAccounts:)` returns a `SeedReport`. Helper `cardIssuerSlugFromCatalogue(catalogue)`.
- `instruments/card_linker.dart`: `InstrumentCardLinker.link(card, userCards:, smsBodies:)` returns `CardLinked`, `CardNeedsProduct` (issuer, digits, at most 3 suggestions from `LocalCardDiscoveryEngine.discoverAcrossMessages`, read-only) or `CardAlreadyLinked`.
- `instruments/bank_summary_adapter.dart`: `bankAccountSummariesFromInstruments(instruments, {manualBalances})` returns `List<BankAccountSummary>`.
- `instruments/issuer_slugs.dart`: today's bank codes to v2 slugs and back (`indus` to `indusind`, `aubank` to `au`, `scb` to `sc`), and issuer names to slugs.

## Decisions and deviations to confirm

1. **`lib/sms_v2.dart` got one export line.** WP-04 lists no touch points, but the package API is exported there (WP-02 did the same).
2. **Golden adapters not wired, as instructed (WP-04.md does not list `adapters.dart`).** To light up the `instruments` stage, apply this to `tools/sms_rules_cli/lib/golden/adapters.dart` (about 20 lines; tested):
   - import `resolveInstrumentsForGolden` from `sms_v2.dart`;
   - in `loadDefaultAdapters` build the `EngineInterpreterStage` first and pass `instruments: _RegistryInstrumentStage(interpreter)`;
   - add `class _RegistryInstrumentStage implements InstrumentStage` whose `resolve` returns `InstrumentResolution(instruments: r.instruments, facts: r.facts)` from `resolveInstrumentsForGolden(facts: facts, knownInstruments: knownInstruments, bundle: interpreter.bundle)`.
3. **`issuerKind: upi_app` does not exist** in the frozen enum (`bank, card_network, wallet, broker, gateway, biller, other`; `SBIUPI` is `bank`). The resolver takes a sender-brand set (`defaultUpiAppSenderBrands`, or any brand containing `UPI`) instead. The golden stage gets no sender, so that rule is covered by unit tests only. If a real `upi_app` kind is wanted, that is a contract change request.
4. **`limitHistory` has no field on `Instrument`** (frozen). It is returned by `applyFact` and stored by `InstrumentStore` as an extra `limitHistory` key in the row's `payload`; `get` strips it, so uploads stay valid.
5. **Mask-less wallets, brokers and pay-later instruments are created** (the work package text reads as "a mask, or a single existing instrument"). The `wallet_topup_then_wallet_spend` scenario needs a mask-less Paytm wallet. Cards, accounts and loans without a mask are never created.
6. **Suffix matching is not done.** An account seen as `123456` and later as `3456` becomes two instruments (the contract's matching order has no such step). Worth a follow-up once real data shows how often it happens.
7. **Seeder choices.**
   - Wallet cards of type `debit`/`prepaid` become `debit_card`/`prepaid_card` (the rest `credit_card`).
   - A card with a non-UUID id (guest cards) or an unknown issuer is skipped and listed in `SeedReport.skipped`; `userCardId` must be a UUID.
   - Accounts need a 4-digit last4 and are dropped when the issuer text matches `upi|axio`, as Home does today.
   - A seeded user-entered credit limit gets source `user`; a seeded points balance gets no `pointsAt`, so any SMS snapshot replaces it.
   - A manual balance is seeded with its own time; the adapter still overlays `manual_bank_balances` (as Home does), so `latestBalanceSmsAt` for a manual row is the manual time, not the older SMS time. The Home and account screens show `manualBalanceUpdatedAt` for such rows.
8. **Store.** Instruments without a mask (wallets, brokers, cards seeded without last 4) are unique by id only, since SQLite treats NULLs as distinct in the identity index. A second id for a non-null key throws `InstrumentKeyConflict`.
9. **Card linker** needs the card's own SMS bodies (they stay on the phone) to produce suggestions; with none it returns the issuer and digits and an empty list.

## How it works

- **Cohort**: `testers` if in `sms_v2_testers`; else `sha256(lowercased profileId)` read as a 256-bit big-endian integer, mod 100: below 5 `pct5`, below 25 `pct25`, else `all`.
- **Manifest** per cohort = `{ruleId: version, "@parts": sha256(parts)}`. A version is visible to a cohort when it has an unpaused cohort row at that cohort or wider. Newest visible version wins; paused versions fall back. Drafts, retired rules and rules never published are excluded. Bundles are minted per cohort only when that cohort's manifest changed; minting order is `all, pct25, pct5, testers`, so the first import yields bundle 1 on `all` (bundles 2 to 4 are the same content on the other cohorts).
- **Serving**: stored body is re-signed at serve time with `expiresAt` = now rounded down to the hour + 7 days. `ETag` is `"v<bundleVersion>-<expiresAt>"`. `304` when `since >= bundleVersion` or `If-None-Match` matches. Response is gzip.
- **Publish gate**: `goldenReport.bundleSha256` must equal `contentSha256` of the candidate bundle for the target cohort. That hash is sha256 of the canonical bundle with `signature`, `bundleVersion`, `createdAt`, `expiresAt` removed (they are not known to the console). The candidate endpoint returns the hash and body so WP-11 and the CLI can run the golden set against exactly that bundle. Report must show all cases passing (`{total, passed}` or the CLI `counts.{cases, casesPassed}`), and each metric in `tools/sms_golden/gates.json` profile `m1` that is present and not `not_available` must meet its bound.
- **Pause** applies to the newest live version of the rule (or `?version=`). **Rollback** copies `toVersion`'s body into a new version on `all` and marks the superseded bundles `rolled_back`. A version can only move to a wider cohort (`cohort_narrowing` 409).
- **Auto-pause**: described in the WP; reason `auto_correction_rate`; the list endpoint returns `autoPaused`.

## Deviations and decisions to confirm

1. **`api/src/portable_backup/coverage.json`** edited (outside the lane): 7 `platform_ops` entries for the new tables, because the existing test `every migration table is classified` fails otherwise and `npm test` must pass. WP-08 will need the same for its tables; expect a trivial merge conflict.
2. **Extra files**: `rules_store.js` (store layer) and the `GET .../candidate` route, both beyond the WP's file list but inside `api/src/sms_v2/`.
3. **`sms_v2_bundles.body`** column added to the Contracts table (serve needs the content, and expiry is re-signed per serve).
4. **`index.js` touch point not made** (file absent), see Wiring.
5. **Pause body has no version** in the schema, so pause targets the newest live version; optional `?version=` added.
6. **"24 hours" window** for auto-pause uses daily rows from the UTC date of now minus 24 h onward, so it spans up to about 48 h of data; stats have day granularity only. Previous-version rate uses the same window.
7. **`devices`** in the daily rollup is the count of distinct profiles (the stats request carries no device id).
8. **Stats upload replaces** the same profile/day/rule/version/app row (assumes cumulative daily counters).
9. **`GET /admin/sms/v2/metrics`** is not built (not in this WP's list); `autoPaused` appears on the rules list. Golden coverage in the detail route is `exampleCount` only.
10. **Gates file**: loaded from `tools/sms_golden/gates.json` (override `SMS_V2_GATES_PATH`). Like the contracts directory it is not in the API Docker image; WP-08 must copy it or set the variable. Publish fails closed if it cannot be read.
11. **Import source**: tested with the contract fixture `bundle/full.json`, since the WP-03 `rules/sms/v2` output does not exist yet. Provisional rules in an import are stored but not released. Imported rules keep their body but are renumbered to version 1.
12. Only `sms_v2_rules` rows in `draft` status are edited in place (a second PUT replaces the open draft); all other rows change only status/body-status on publish or pause.

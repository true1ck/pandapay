## What was built

- Domain library `package:pandapay_domain/sms_v2_ledger.dart`: `DefaultLedgerProjector`, `LedgerSnapshot`, event classification, instrument attribution and card usage.
- The projector follows the contract's spend/income/investment/transfer table. Card bills and own transfers are one own-to-own entry, holds produce no entries, IPO investment is the sum of actual debit legs, and duplicate/original legs never add money. Rejected instruments do not create money projections. Known brokers and own-transfer destination masks resolve to own endpoints.
- Totals use integer paise, half-open time ranges, unique entry ids and unique counted events. Refunds reduce spending; withdrawals reduce net investment. Purchase categories remain available for refunds outside the purchase's reporting period.
- `LedgerStore`: per-account storage, atomic event replacement, period reads, dirty/clean operations and contract-safe round-trips.
- `ProjectionWriter`: ledger and existing transaction rows share one SQLite savepoint. Stable `v2:<eventId>` identity, anchor source key, method, card/account digits, category ids, SMS receipt time and pipeline metadata are mapped to `TransactionEntry`. An event that ceases to have money retires its display row. Reprojection preserves server reward values, notes and tags.
- App adapters: subscriptions and mandate lifecycle, failed attempts without extra charges, calendar-aware next monthly date, bills and per-card statement ledgers, payment allocation without reuse between cycles, partial card payments, investments/withdrawals/fund balances/dividends, IPO state and Money in including repeated-payer salary detection.
- `CardStateAdapter` applies learned limits/points through the existing repository only when the current value is empty or matches explicitly supplied last-applied SMS state. Existing manual values are protected. WP-14 must persist and supply that state; this adapter does not start background/network work by itself.
- `LedgerReadModel` converts retained legacy/manual/email transaction rows into ledger inputs for compatibility, then uses the same totals functions. Home, Activity, Insights, category and method breakdowns, filtered Spending, subscriptions, bills and card-usage providers have guarded reads.
- `TxnEntryKind.refund` and `unknown`; unknown future kinds stay unknown. Historical `payment` is an explicit spend alias because the unchanged receipt-reconciliation regression requires it. Existing dropdown choices stay the same; refund/unknown are included only when already on the edited row.
- Golden harness projector/category stages are now available. `tool/check_pipeline.dart` builds from rule source, validates examples and lint, signs with an ephemeral in-memory key, and runs the complete harness. CI runs it with the committed baseline and regex parity.

## Design and integration decisions

1. **Refund categories without a schema change.** The frozen contract forbids category on an external-to-own ledger row. Refund rows remain valid. `LedgerSnapshot` computes refund decisions from facts and links; `LedgerStore` persists `_categoryDecision` as local payload metadata and strips it from typed/wire JSON. Totals receive the category map explicitly. Cross-device transport of standalone refund category context remains a WP-14 integration question; do not assume local metadata is on the wire.
2. **Reporting readiness.** `SMS_PIPELINE_V2` enables new reporting only after this account has v2 facts/events. Before replay produces data, retained v1 history keeps its established source. Capture routing will still use the build flag, not reporting readiness. An upgrade-transition widget test covers this behavior.
3. **Fixture period correction.** November IST is `[2026-10-31T18:30:00Z, 2026-11-30T18:30:00Z)`. Original UTC-midnight fixtures excluded date-only 1 November transactions. Expected money values were not changed; see `requests/WP-06-golden-period-timezone.md`.
4. **Amount-less failed attempt.** The request from WP-03c is resolved using its golden-fix option: the unchanged synthetic message expects review. No fake amount, ignore rule or schema change. It still contributes to capture recall and ask rate.
5. **Integration touch points** are recorded in `requests/WP-06-integration-touch-points.md`. No Gmail/email/IMAP/card-discovery code changed. No migrations or frozen schemas changed.

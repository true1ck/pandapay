## How ingestion works

One database transaction per request, under the same per-profile advisory lock `insertTransactionAndUpdateState` takes (`transaction-ingest:<profile>`), so v1 and v2 writers never interleave and `updated_at` (written with `clock_timestamp()` after the lock) is monotonic per profile. Order: instruments, facts, events (then the `afterEventsStored` hook), ledger, `transactions` projection.

- **Facts** `ON CONFLICT DO NOTHING`; a conflict is `duplicate` when the row is the profile's own, else `rejected: fact_id_conflict` (an id owned by another profile is invisible to RLS and never revealed). `info` facts, evidence spans and `instrument.raw` are refused by the contract and never stored. Each fact is linked to the stored instrument matching its mention (kind + issuer + mask).
- **Instruments** upsert by id. A different id for an existing key (or two ids for one new key in one request) is `rejected: instrument_key_conflict` with `errors[0].path = "existingInstrumentId:<uuid>"` (the response schema only allows `code` and `path`). A `userCardId` the profile does not own is `instrument_user_card_unknown`. Merge on update: a user-entered credit limit is never overwritten by SMS; `available_*` and `points_*` keep the value with the later timestamp; first/last seen and evidence count only widen.
- **Events** upsert; stored legs stay first and only grow (omitted legs are kept, a leg cannot change role: `event_leg_role_conflict`). Status rules: `awaiting_leg` to `complete` or `ambiguous`, `ambiguous` to `complete`, anything to `user_confirmed`, nothing leaves `user_confirmed` (`event_status_locked`); other moves are `event_status_transition_invalid`. A leg whose fact is neither in the request nor stored for the profile is `event_leg_fact_unknown`.
- **Ledger** upsert by id. `ledger_event_unknown` if the event is not stored. An own to own entry (both ends an instrument or `ownUnresolved`, unit INR) must equal the posted amount of the event's `debit_leg` facts, or its `credit_leg` facts when there is no debit leg (`ledger_own_amount_mismatch`).
- **Result statuses**: `accepted` when something was written, `duplicate` when the merge changed nothing (timestamps compare as instants), `rejected` with a server code (not in `error_codes.json`, which only lists contract codes).
- **`transactions` projection** for every event stored or whose ledger entries changed. Kind per the Contracts table; `ipo_application` is a row (`investment`) only once a leg is `hold_converted` or `debit_leg`; `unknown` and zero amounts are no row. Fields: `pipeline_version = 2`, `source = 'sms'`, amount = `event.amountMinor / 100`, merchant = the external end of the first INR ledger entry, `category_id` from the slug (unknown slug gives null), `user_card_id` from the instrument (only for a credit or debit card row, because of `transactions_card_matches_instrument`), `instrument` and `rail` mapped as the v1 import does (UPI is `upi_qr`, ATM `atm`, EMI `emi`, the rest `unknown`), `source_key` = the anchor fact's `sourceKey`.
  - A v1 row with the same `source_key` (and no `event_id`) is **adopted**: `event_id` and `pipeline_version = 2` are set, nothing else, card state is not touched. A second event anchored on an already used `source_key` gets `<key>#<first 12 hex of the event id>`.
  - **Card state** (`applyTransactionState` through `deps`) is applied once for a new credit-card spend with a loadable card, never for `?backfill=true` (the row is stored with `is_backfill = true` and is never applied later either). If a row's amount, category, date or card changes, the old effect is reversed (`reverseTransactionState`) and the new one applied. An event that stops counting retires its row (`status = 'ignored'`) and reverses its state. No duplicate detection and no `transaction_observations` rows are written for v2 (the linker is the dedupe).
- **Sync**: cursor is base64url JSON of `(updated_at at microsecond precision, id)` per entity (plus optional hook cursors). 1,000 rows per entity per call.

## Deviations and decisions to confirm

1. **`hasMore` is a header, not a body field** (`X-Sms-Sync-Has-More: 1|0`): the frozen `sync.response` schema forbids extra properties. Request filed: `requests/WP-08-sync-hasmore.md`. Until it is decided WP-14 should read the header or treat a 1,000-row list as "more".
2. **`?backfill=true` query flag**: the frozen `facts_batch` request has no `backfill` field, so the flag is a query parameter.
3. **Registration sits before the global JSON body parser** in `api/src/index.js` (not next to the other routes). The global parser is capped at 100 KiB and would reject a 1 MB batch before it reached any later route. `registerSmsV2` reads the facts body itself (1 MiB as sent, 8 MiB inflated, gzip or plain) and adds the standard parser under `/sms/v2` and `/admin/sms/v2` after the flag check, so rule routes and later work packages still get `req.body`. A flag-off request is turned away before any body is read. Auth, logging and CORS middleware still run first.
4. **Docker image**: the build context is `api/`, so `api/sms_v2_assets/` holds a copy of the schemas, `error_codes.json` and `tools/sms_golden/gates.json`; the Dockerfile copies it and sets `SMS_V2_CONTRACTS_DIR` and `SMS_V2_GATES_PATH`. `npm run check` (so `npm test`) fails if the copy differs from its sources; fix with `node api/scripts/sync_sms_v2_assets.js`. Any future contract change request must run that script. (The alternative, a BuildKit named context in three compose files and the CI build step, would break builds on a compose version without `additional_contexts`.) Verified: the image builds and `contracts.js` loads in it.
5. **No signing key does not stop the API starting**: WP-09's `signerFromEnv()` throws in production without a key; `registerSmsV2` catches that and passes `signer: null`, so rule routes answer 503 `signing_unavailable` while everything else boots.
6. **Security hooks** for the rule routes are passed as per-call delegates, so a later WP-13 assignment to `hooks.security.*` reaches them. `checkRate(req, 'facts:batch', itemCount)` and `checkRate(req, 'sync', 1)`: `false` or `{ok:false}` gives 429; `verifyAttestation` false gives 403; a throwing hook gives 503.
7. **Hook return shape**: `aiResultsSince` / `correctionStatusSince` may return an array, or `{items, cursor}` with a string cursor that is stored in the sync cursor and passed back (`hooks.aiResultsSince(profileId, previousHookCursor)`).
8. **`user_cards` link**: an instrument's `userCardId` is a real foreign key (`on delete set null`); ledger endpoints and `parent_instrument_id` are plain uuids (no FK, so order within a request does not matter).
9. **Event type changes** with legs growth are allowed (the linker may re-type an event); only status is constrained.
10. **Extra files** inside `api/src/sms_v2/`: `projection.js`; and `api/scripts/sync_sms_v2_assets.js`.
11. `work-packages.md` status was not changed (orchestrator).

## For the next packages

- Add your registration line at the end of `registerSmsV2` in `api/src/sms_v2/index.js`; use `shared`-style deps (`requireSmsV2`, `requireMember`, `withUserClient`, `hooks`). Read `hooks.x` at call time, never copy it at registration.
- `afterEventsStored(client, profileId, events)` runs inside the batch transaction, only when something was actually stored or changed, before ledger entries are written (the ledger entries of the same request are not yet stored when it runs).

# Join identity: full phone for the owner, consent, unique names (Phase 1 spec)

Single source of truth for the backend and app work. Branch `split-labels`. Nothing is pushed. Decisions below were approved by the product owner; where a number or limit is written here, implement exactly that.

## 1. Decisions (approved)
1. **Consent**: before a link-only or group-link join request is sent, a claimant who HAS a verified phone must choose one of two options (neither pre-selected): "Share my number" or "Ask without sharing". Claimants with no verified phone (email-only accounts) see a notice only. The choice is sent as `sharePhone: true|false`. Missing `sharePhone` (old app) is treated as `not_asked` and the full number is NOT stored.
2. **Refusal allowed**: a request without a shared number is accepted; the owner sees "Did not share a number". Such requests are excluded from any bulk approve (later phase) and show a stronger warning.
3. **Retention**: the encrypted full number is deleted (column nulled, `phone_purged_at` set) on approve, decline, expiry, remove, claimant cancel, and account deletion. The 4-digit suffix and the HMAC hash stay (hash is dropped at account deletion). Lazy purge inside every function that touches an invitation + an hourly purge function for rows past `expires_at + 24h`.
4. **Audience**: only an ACTIVE OWNER of that context ever sees it, only while the request is pending (`state='awaiting_owner'`, not expired). Never other members, never push, never sync events, never list payloads in the clear.
5. **Reveal requires**: caller is an active owner; request pending and unexpired; `phone_share='shared'` and not purged; the owner has a verified phone themselves (a `phone_directory` row for the owner's profile); reveal caps 5/hour and 30/day per owner (advisory-lock based like `lookup_phone`). Every reveal inserts an audit row (no number in it).
6. **Copy button** allowed on the revealed number (app copies digits with +cc only; clears the clipboard after 60 s if it still holds our value).
7. **Masking (adaptive)**: default view `+91 72••• •4821` = country code + first 2 national digits + last 4. For a number whose national part is shorter than 8 digits show cc + last 3 only. If two or more PENDING requests of the same owner (or a pending request and an existing member of the same context) have the same visible mask but DIFFERENT hashes, flag `lookalike=true` and return the FULL number for those items directly (no tap), and the app underlines the differing digits. If same hash => `duplicateOf` (same number, possibly two accounts).
8. **Unique names**: see section 5.

## 2. Storage (one additive migration `20261116100100_shared_expense_join_identity.sql`; keep the existing 20261116090000 untouched)
New columns on `shared_expenses.invitations`:
- `claimant_phone_enc bytea NULL`, `claimant_phone_key_id text NULL` (AES-256-GCM done IN NODE; nonce+tag packed in the bytea; AAD = invitation_id bytes; key ring from env `SHARED_EXPENSE_PHONE_ENC_KEYS` = JSON `{"current":"k1","keys":{"k1":"<base64 32 bytes>"}}`; refuse to start capture (fail closed: store no number) when the env is missing; never reuse ENCRYPTION_KEY or SHARED_EXPENSE_INVITE_SECRET)
- `claimant_phone_cc text NULL` (e.g. `+91`), `claimant_phone_hash text NULL` (same HMAC as the directory so it is comparable with `phone_directory.phone_hash` / `target_phone_hash`)
- `claimant_phone_mask text NULL` (precomputed default mask, e.g. `+91 72••• •4821`, never the full number)
- `phone_share text NOT NULL DEFAULT 'not_asked' CHECK (phone_share IN ('shared','declined','none','not_asked'))` ('none' = claimant had no verified phone)
- `phone_captured_at timestamptz NULL`, `phone_purged_at timestamptz NULL`
- keep `verified_phone_suffix` as is (still 4 digits or NULL) and still populated.
New table `shared_expenses.phone_reveals(reveal_id uuid pk, invitation_id uuid, owner_profile_id uuid, at timestamptz default now())` RLS-forced, definer-only, no number inside. Index (owner_profile_id, at).
Same owner/grants/RLS pattern as the existing invitation objects (shared_expenses_owner, SECURITY DEFINER, `SET search_path=pg_catalog,shared_expenses,pg_temp`, REVOKE FROM PUBLIC, GRANT EXECUTE TO app_user only where the API calls it as the user).
- Claim functions (`claim_invitation`, `_claim_group_link`, accept-by-id) get new OPTIONAL params with defaults (cc, hash, mask, enc bytes, key id, share flag) so old callers keep working; the API passes them. FIX the re-claim early return in `_claim_group_link` (and `claim_invitation` pending branch): while still pending, a re-claim refreshes suffix/hash/mask/enc/share/captured_at (and re-applies consent) instead of returning the stale row. Also FIX the zombie bug: `_claim_group_link` must treat expired `awaiting_owner` rows as expired (check `expires_at > clock_timestamp()` in the pending lookup AND in the 20-pending cap count), and a claim that moves a request to `awaiting_owner` resets `expires_at = clock_timestamp()+interval '7 days'`.
- Purge hook (`_purge_claimant_phone(p_invitation uuid)` or set-based) called from respond_invitation (both outcomes), decline paths, remove_member, leave paths, link revoke, account-deletion/erasure path (find it: members erasure, `erased` state, profile delete cascade) which must ALSO null `claimed_profile_id`, `verified_phone_suffix` and all `claimant_phone_*` on invitations of that profile. Hourly `purge_expired_claimant_phones()` (register in the cron pattern used by `0013_cron_jobs.sql` only if pg_cron exists; the function must be callable and tested directly).
- `list_join_requests` / `list_invitations`: keep every existing key with the same names/semantics (flat suffix keys stay 4-digit-or-null forever). ADD key `claimantPhone` per item:
```json
"claimantPhone": {
  "v": 1,
  "source": "verified | none",
  "consent": "shared | declined | not_asked | none",
  "countryCode": "+91",
  "last4": "4821",
  "mask": "+91 72••• •4821",
  "available": true,

  "duplicateOf": [],
  "numberStatus": "confirmed | moved | unknown",

```
No `e164` in lists, ever. `unavailableReason`: `claimed_before_update` | `claimant_declined` | `no_verified_phone` | `purged`. `numberStatus`: compare `claimant_phone_hash` with `phone_directory` (same profile holds it => confirmed; another profile => moved; no row => unknown). When `lookalike=true` the list item additionally carries `fullNumber` ONLY for lookalike items and ONLY when the caller passes `?withLookalikeFull=1` (decryption happens in Node, never SQL). Node decrypts in the route handler; the SQL returns the ciphertext only to Node via a separate definer function (`list_join_requests_enc`) that is NOT granted to app_user directly... - Reveal: `POST /shared-expenses/invitations/reveal-phone {invitationId, operationId}` -> 200 `{invitationId, e164, revealedAt}`; 409 `phone_not_available`; 403 `context_not_authorized`; 429 `reveal_rate_limited`; 400 invalid. `Cache-Control: no-store`. The response is NOT stored in the operation ledger (store a redacted marker only). Never logged. For phone-bound invites `matchesTyped` can also be derived from `target_phone_hash` and returned as `claimantPhone.matchesTyped` (true/false/null).

## 3. Phone handling rules (API)
- The claimant's full verified number comes from the auth session (`verified_contacts.phone.value`, see api/src/auth.js). It may be null (email-only account or unverified) -> `source:'none'`, `phone_share:'none'`.
- Align `normalizePhone` in api/src/shared_expenses/invitations.js with auth: accept E.164 with >=7 digits after `+` (today it rejects 7-digit numbers and would 400 the claim). Keep ASCII-only digits; reject any other character.
- Country code: use `libphonenumber-js` (pin an exact version, install in api/, update lockfile) to parse E.164 -> country calling code + national number; never use `users.country_code` from auth. If parsing fails, fall back to cc = '' and mask = last 4 only; never throw because of display data.
- Mask = cc + space + first 2 national digits + `•` for each hidden digit grouped in the same shape + last 4; for national numbers < 8 digits: cc + `•••` + last 3. The mask must never contain more than 6 digits.
- Encrypt with AES-256-GCM, random 12-byte nonce, AAD = invitation id; key id stored; decrypt with the matching key; support rotation (decrypt old key ids, encrypt with current).
- The plaintext number must NEVER appear in: SQL parameters logged by pg, the operation ledger `_finish` payload, `invitation_audience`, push/notification rows, error messages, API request logs, `console` output, test snapshots. Add regression tests that grep logs/notifications/ledger for the digits.
- `invitation_audience` and notifications.js must not gain any phone field.

## 4. Sanitising (names shown on join cards)
- `claimantName` / `claimantProfileName` in join-request output must pass the same cleaner as member labels (strip C0/C1 controls, bidi controls U+202A-202E U+2066-2069 U+200E/F, zero-width U+200B-200D U+2060 U+FEFF, collapse whitespace, cap 40 code points). Update `_clean_label`/label.js to ALSO strip those bidi/zero-width characters. Group-link placeholder labels (derived from the profile name) go through it too.

## 5. Unique names (approved: do not allow duplicate names)
- Normalised key `label_key(text)` = lower(NFKC(text)) with all non-alphanumeric characters removed, plus a small confusable fold (Cyrillic/Greek letters that look Latin -> Latin: а е о р с у х к т м н в і ј and Greek ο ν α ρ -> latin equivalents). SQL function `shared_expenses._label_key(text)` (IMMUTABLE) and the same function in Node (api label.js) with a shared test vector file `contracts/shared_expenses/v1/label_key_vectors.json`.
- **Within a split (group or direct)**: a typed label must be unique by `label_key` among the other members of the context whose state is `active` or `invited` (including the owner's own typed label if any, and the "live" names of already-joined members are NOT compared, only stored labels + effective labels via `_member_label`). Violation -> HTTP 409 `member_name_taken` (SQLSTATE 23505 style like other conflicts). Applies to member.invite, member.rename, group-link placeholder creation (the generated label gets a numeric suffix ` (2)`, ` (3)` instead of failing), and add-member paths. Renaming a member to its OWN current label (no change, or only case/spacing) is allowed. Legacy duplicates already stored are grandfathered; they are only checked when the label changes.
- **Across the creator's friends (direct splits)**: `context.create` for kind `direct` is rejected with `friend_name_taken` when the creator already has another ACTIVE direct context whose counterpart typed label has the same `label_key`; the response includes the existing contextId so the app can offer "Open existing". The app's old 'Add anyway' option is removed. Renaming a friend to a name already used by another friend is also rejected the same way (rename of a direct counterpart must check the creator's other direct splits).
- **Reserved labels** (compare by label_key): you, me, myself, owner, admin, support, someone, pandapay, pandapayfriend, formermember, unknown, deleted. -> `member_name_reserved` (400).
- Race safety: enforce inside the context row lock (`FOR UPDATE` already taken by the commands) and back it with a partial UNIQUE index on `(context_id, shared_expenses._label_key(display_name)) WHERE state IN ('active','invited') AND display_name IS NOT NULL AND legacy_dup_ok IS NOT TRUE` is NOT possible with grandfathered duplicates; instead use `pg_advisory_xact_lock(hashtext(context_id::text))` in the functions that write labels and check inside the lock. Document the choice.
- Idempotency: replaying the same operation id returns the stored result (including a stored conflict) as today.

## 6. App (Flutter) requirements
- Join screen (`runtime/shared_join_route.dart`): show who owns the group (if the preview has it) and, for claimants with a verified phone, the two-option choice (radio pair, neither selected, button disabled with hint until chosen), showing the claimant's own MASKED number and copy: "{owner} will see your PandaPay name and your phone number (+91 72••• •4821) to confirm it is you.

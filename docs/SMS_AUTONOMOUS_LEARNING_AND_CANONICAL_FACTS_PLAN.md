# SMS autonomous learning and canonical facts: implementation plan

**Status:** supporting implementation detail, 22 October 2026. [The final autonomous implementation plan](SMS_INTELLIGENCE_FINAL_AUTONOMOUS_IMPLEMENTATION_PLAN.md) is the authoritative handoff. This document describes work still to be verified and built; it does not claim the autonomous learning loop is implemented. Read it with [the master plan](SMS_INTELLIGENCE_MASTER_IMPLEMENTATION_PLAN.md), [the existing flow compatibility audit](sms-existing-flow-compatibility-audit.md), [the single decision intake plan](SMS_SINGLE_DECISION_INTAKE_IMPLEMENTATION_PLAN.md), and [the message families plan](sms-message-families-plan.md). No admin must routinely author or approve a learned rule. Admin controls remain for visibility, pause, and emergency rollback. No UI redesign is required.

**Research decision:** [SMS learning technique research and final architecture decision](SMS_LEARNING_TECHNIQUE_RESEARCH_AND_DECISION.md) compares rules, scored classifiers, Gemini, weak supervision, template synthesis, and online model training. Its chosen approach is a restricted-template, calibrated-abstention, Gemini-fallback pipeline with independent labels and staged automatic rollout. Implement that design; treat an on-device trained model as an optional, measured later improvement, not a prerequisite. The research document's risk-tiered evidence requirement governs promotion when a cluster has only a few users.

## 1. Outcome and exact boundary

An SMS is captured once under the existing user-scoped source key. The device makes one durable safety/relevance decision. An eligible SMS produces zero or more versioned, typed facts. Existing product projections consume those facts instead of independently re-reading and re-parsing the SMS body. When an unknown format is corrected or independently resolved, a server learning worker groups comparable examples, proposes a restricted rule, tests it against positive, negative, mixed, historical, and cross-platform cases, runs it in shadow, gradually enables it, and rolls it back automatically if quality falls. New users download only rules that have passed these gates.

“Self learning” here means automatic improvement of classification, field extraction, entity binding, and cross-message inference policies. It does **not** mean silently retraining Gemini weights, accepting Gemini's own confidence as proof, or immediately turning one user's SMS into a global rule.

**User-facing decision loop:** a clear, well-evidenced promotion is filtered on-device. A plausible financial SMS that rules and Gemini cannot resolve remains durable and appears in the existing Needs Review page, where the user can confirm/edit the financial facts or mark it not financial. That choice resolves the source for this user immediately. It seeds a narrow learning candidate for other users only when contribution is allowed; the next user receives automatic filtering/extraction **after** the shared candidate passes independent positive/negative evaluation and staged promotion. Before promotion, the next user may receive a prefilled suggestion, but the app does not silently apply a one-user label globally. If Gemini is unavailable, the same review fallback applies after bounded retry.

The old scan, future-message listener, source-key deduplication, receipts, offline recovery, user overrides, and existing transaction/bill/balance/card/mandate/subscription behavior are compatibility gates. A rule update must not reset the inbox cursor or create a second economic event for an already processed SMS.

## 3. Canonical source and interpretation model

Retain the existing captured SMS/outbox and `sms_sources`, `sms_source_facts`, `fact_overrides`, transaction receipts, and inbox progress. Add versioned decision metadata rather than introducing another raw-body store. A proposed device `sms_source_decisions` table and server equivalent should hold: namespace/profile, source key, received time, sender family, decision (`safety_excluded`, `noise`, `financial`, `unresolved`), reason codes, triage/parser/bundle/model versions, processing state, fact-set hash, confidence/calibration version, user-override revision, and timestamps. Persist no raw OTP. A clear promotion/unrelated message needs only a minimal idempotency receipt; keep raw financial context on the device under the existing retention policy.

Each accepted fact has source key + stable fact identity, family, typed payload, amount/date role, extraction provenance, version, validation status, supersession relation, and field/entity confidence. Keep `posted_movement`, `balance_snapshot`, `bill_obligation`, `bill_payment`, `mandate_lifecycle`, `pending_or_failed_attempt`, `card_identity_hint`, `security_or_service_alert`, and `promotion` distinct. A source can yield several facts. Source and fact writes, outbox insert, and scan checkpoint must be crash recoverable. Reprocessing a source replaces/supersedes eligible machine facts; it never overwrites a user override or inserts a second posted event.

Product consumers should read accepted facts or projections derived from them:

| Consumer | Fact or inference input | Required guard |
| --- | --- | --- |
| Activity, reports, spending | `posted_movement` | Only posted money affects totals; pair transfers and card repayments before spend metrics. |
| Bank balance | `balance_snapshot` | Show the latest observation **as of its SMS time**, not a fabricated current balance. |
| Credit card bills and Payments Due | `bill_obligation` + `bill_payment` | Distinguish total/minimum/outstanding, statement date, due date, and cycle identity. |
| Mandates | `mandate_lifecycle` | A registered ceiling or scheduled attempt is not a posted debit. |
| Subscriptions | Series of posted charges, bill obligations, and mandate evidence | Learn cadence and provider identity over multiple independent sources; allow amount/date variation; avoid duplicate series. |
| Card/account matching | Card/account hints plus user inventory | Last four digits are supporting evidence, not a unique global ID. |

## 4. Automatic learning data and labels

The current contribution opt-in remains authoritative. A correction always works for its user; cross-user learning uses only consent-eligible examples. No new screen is required for this phase. If there are too few eligible examples, the worker stays at candidate/shadow state rather than inventing evidence.

Create an encrypted, access-limited learning-example store with retention and deletion rules. Store a redacted **template shape** (stable words and typed placeholders such as `AMOUNT`, `DATE`, `LAST4`, `REFERENCE`, `NAME`), sender family/fingerprint, source/fact identity, baseline and corrected labels, explicit outcome (`confirmed`, `edited`, `dismissed`, `missed_financial`, `subsequently_contradicted`), field-role spans or safe anchors, parser/model versions, and provenance. Keep user mapping and raw text separate. Do not distribute individual examples to devices, log them, or show them in the ordinary admin dashboard. Sensitive-message vetoes (OTP/PIN/CVV/security) happen before example creation.

Collect **positive and negative** evidence. A corrected amount/due date is one positive example for the corrected role and one negative example for the old extraction. A dismissal is a negative label for the proposed fact, but not proof that every similarly worded sender message is noise. Gemini agreement with its own earlier output is not independent evidence. Accept independent user action or later reconciled product evidence as stronger labels; record the label source and reliability. Split train/evaluation by source, user, issuer template, and time so near-duplicate messages from one user cannot leak into the holdout.

For missed financial messages filtered before review, add a privacy-safe discovery channel: opted-in user import/diagnostic correction and bounded audits of minimal negative receipts. Never require a full inbox rescan on each launch. Any historical re-evaluation is an explicit, versioned migration using the existing source key and receipt path.

## 5. Candidate generator and evaluator

Run a durable, rate-limited server worker. It consumes new eligible labels and uncertainty clusters, not every incoming SMS. Cluster by sender family, stable wording anchors, fact family, and slot layout; separate promotional, statement, transaction, mandate, and service variants even when the sender matches. Generate a restricted declarative template or regex with typed captures and required/excluded anchors. Gemini may propose a candidate for a difficult cluster; its output must pass the same compiler and evaluator as a deterministic proposal.

Extend the existing JS/Dart rule contract only through a versioned schema. The current downloaded format supports movement, balance, bill, mandate, and ignore rules; other families and multi-fact templates need explicit contract additions or must remain server-only. Do not ship arbitrary executable code or an unsupported regex dialect. Bound pattern length and work, test adversarial input, capture-group indices, amount/date roles, sender scope, and exact JS/Dart parity. A rule that extracts a bill must not also create spending. `ignore_noise` has the strictest gate and cannot suppress a credible financial fact.

For each candidate, persist a frozen evaluation set and machine-readable report: positive match/extraction accuracy; hard negatives (OTP, marketing with amounts, EMI solicitation, service notice, failed/pending, bill versus payment, balance versus credit limit); mixed financial+offer; historical messages; other issuers; malformed/missing fields; performance; parity; and projection deltas. Keep examples from users and times not used for generation. Reject overlapping candidates that would change an existing high-confidence rule without a measured gain. Measure per-field amount/date/entity correctness, not just family classification. Require enough independent users and examples for the candidate's scope; a one-user pattern can remain user-specific.

Use **family-specific calibrated gates** derived from a labeled corpus. Do not hard-code one “80% confidence” rule. Posted money and entity binding need a much stricter precision target than review suggestions; automatic ignore requires evidence that useful financial messages are not lost. Until enough labels exist to estimate a gate, abstain and keep the existing deterministic/review path. Every candidate records why it passed or failed.

### Scoring for device filtering and fact acceptance

Use a **hard-gate + calibrated-score + abstention** design. Research on [probability calibration](https://proceedings.mlr.press/v70/guo17a.html) explains why a raw model confidence should not be read as an observed correctness rate; [selective classification](https://papers.neurips.cc/paper_files/paper/2017/hash/4a8423d5e91fda00bb7e46540e2b0cf1-Abstract.html) formalizes the tradeoff between automatic coverage and error when the classifier can abstain. For this app, keep the hard gates for secrets, invalid payloads, and user overrides. A score never overrides those gates.

1. **Score distinct questions.** Estimate `P(useful financial fact)`, `P(pure promotion/unrelated)`, then per-family and per-field correctness (`posted movement`, `bill`, `balance`, `mandate`; amount/date/identity). These are separate outputs, not one SMS confidence number. A bill may be certain while its due date or card match is uncertain.
2. **Start with explainable evidence.** Device features can include completed-versus-conditional verbs, currency/amount context, due/statement/balance anchors, sender family, rule match quality, offer wording, negation, and conflict signals. A small fixed-weight or logistic model is an optional next step after labeling; the first release may calibrate existing rule evidence. Do not introduce an opaque on-device model merely to produce a percentage. Version features, weights, and calibration with the rule bundle; retain the built-in fallback offline.
3. **Route by asymmetric cost.** A hard security exclusion is immediate. Mark as noise only when evidence for financial usefulness is below a threshold validated for very low missed-financial risk, and the promotion/unrelated evidence is independently strong. Clear financial messages continue to extraction. Middle cases stay durable and go to server rules/Gemini, then Needs Review only if actionable uncertainty remains. Never discard solely because a financial score is below an arbitrary 0.80.
4. **Gate each resulting fact.** Automatic posting requires valid required fields, no contradictory lifecycle/amount/date cues, a calibrated family/field score above its measured gate, and an adequately resolved entity. Balance and bill facts have their own gates. If the family is known but one field is uncertain, retain safe facts and review only the disputed field or binding. A Gemini numeric confidence is supporting evidence, not calibrated proof.
5. **Calibrate and monitor.** Fit score mapping and decision thresholds on consent-eligible, labeled, time-separated examples; evaluate by issuer, language/template, user cohort, and message family. Report reliability plots, precision/recall, false financial discards, false posted events, review load, and coverage at each threshold. Freeze thresholds with the rule version; recalibrate only through shadow and canary rollout. If drift, sparse labels, or a new sender makes calibration unreliable, abstain.

The release criterion is a **risk/coverage curve**, not a preferred percentage: choose the largest automatic coverage that meets the protected error bounds and beats the active pipeline. The initial numeric thresholds must be chosen from the baseline corpus and then recorded in the evaluation report; the example “80%” has no special standing.

## 6. Autonomous promotion, monitoring, and rollback

Candidate states: `proposed → evaluated → shadow → limited → expanded → active`, with `rejected`, `paused`, and `rolled_back` terminal or control states. Transition is driven by a system worker with a narrow database function/service identity, optimistic version checks, and an immutable audit record. The admin publish route remains for emergency operations and manually authored fixes; routine success needs no admin click.

In shadow, run the candidate beside the current interpreter and save redacted disagreement/quality metrics without changing user facts. In limited rollout, assign stable cohorts by profile and bundle version, so the same user does not switch rules on every request. Increase exposure only if correction rate, false review rate, missed-financial rate, invalid facts, duplicate posted events, bill-date errors, and per-family projection deltas meet the evaluated gates. Automatic rollback deactivates the bad version and restores the last known-good bundle; devices keep a validated cached version or built-in fallback. Never roll back user corrections. Keep previous bundle versions and evaluation artifacts for audit.

The bundle endpoint must deliver exactly one selected active version for a cohort and `minClientVersion`, with integrity verification and a monotonic/rollback-aware cache. An invalid update must not displace the last valid cache. Rules learned on the server are used there and downloaded to devices only after their client compatibility gate passes. Source decisions retain the applied version so selective replay and incident analysis are possible.

### Non-regression contract: improvement must be demonstrated

No system can prove that a new rule will never misread an unseen SMS. Treat “only improve” as a strict release policy with abstention and fast recovery:

1. **Compare against the current active pipeline, not a static target.** Freeze a baseline and run old and candidate logic on the same held-out messages. A candidate must improve its intended family/field while preserving every protected invariant below. “More messages auto-classified” alone is not an improvement.
2. **Zero critical regressions in the protected corpus.** Block promotion if a candidate sends an OTP/security message to the server or Gemini, discards a known financial message as marketing, invents a posted debit/credit, duplicates a transaction, changes an amount/date role, changes a user override, or attributes a bill/balance to the wrong account. Include historical failures and every prior production rollback in this corpus. Add newly found incidents permanently.
3. **Bounded scope and precedence.** A new rule may claim only its evaluated sender/template/family scope. It cannot override a user decision, the safety gate, or a higher-priority validated rule. Broad `ignore_noise` rules and cross-issuer rules require stronger independent evidence than issuer-specific extraction rules. If two rules conflict, abstain or retain the last known-good interpretation.
4. **Field and product checks.** Compare exact amount, due date, statement date, balance as-of time, lifecycle, card/account binding, and subscription-series identity. Replay downstream projections; block a candidate that raises false spending, hides an obligation, or changes a settled bill without a supported fact. A correct message-family label cannot compensate for a wrong value.
5. **Independent evidence and minimum sample.** Require held-out users and time periods, enough positive and hard-negative cases to estimate error bounds, and a measured gain over baseline. A cluster with insufficient evidence remains a private candidate or shadow rule, even if Gemini is confident. Never promote on repeated copies from one device or on model agreement with itself.
6. **Shadow and canary stop gates.** During shadow, no user state changes. During limited rollout, continuously compare new and old decisions for the same source where possible and monitor confirmed corrections, dismissals, missed-financial reports, invalid facts, duplicate events, bill-date errors, and per-family financial totals. Predefine minimum sample and maximum error bounds in the evaluation record. Pause expansion immediately on a critical invariant breach; automatically roll back on a confirmed regression or breached bound. A lack of labels is not a pass.
7. **Reversible release.** Keep the prior bundle and projection inputs, version every decision, and make rollback idempotent. Revert machine interpretations only where safe; preserve user corrections and receipts. Re-evaluate affected unresolved sources under the last known-good rule without resetting the inbox cursor or reposting economic events.

Automatic learning should be **additive by default**: a narrow, well-evidenced new format can gain coverage, while existing recognized formats continue through their proven rules. Replacing or broadening an active rule requires a separate comparison and stricter rollout. This policy deliberately prefers Needs Review over an unproven automatic financial write.

## 8. Mandatory scenario matrix

1. First install with mixed inbox: one paged scan, no OTP raw persistence, promotion not sent to Gemini/review, financial facts visible offline, no repeated scan after restart.
2. Same SMS via broadcast, inbox, backup, upload retry, and AI retry: one source, one fact set, one posted event, one user decision. SMS arriving mid-scan or upload is not lost.
3. Same sender/body on separate days: characterize existing source-key collision; propose and test a separate identity migration before changing key semantics.
4. Completed debit/credit/refund/reversal with offer footer and `-P` sender: keep financial facts. Pure spend-threshold/cashback/loan/EMI offer: minimal noise receipt only.
5. OTP/security and call-forwarding/service notices that contain card/transaction/amount words: never become posted money, Gemini input, or Needs Review transaction.
6. One SMS with debit plus available balance: two facts, one posted movement. Balance-only SMS updates latest balance with its observation date.
7. Bill total, minimum, statement date, due date, bill payment, partial payment, and changed due date: preserve separate roles/cycles; no duplicate purchase or wrong due date.
8. Mandate registration, scheduled collection, failed collection, cancellation, and actual AutoPay debit: correct lifecycle, no ceiling-as-spend, and one posted debit only when it occurred.
9. Subscription with variable amount/date, multiple merchants sharing a name, paused/cancelled mandate, and one-off repeat purchases: series inference uses multiple sources and can abstain.
10. User correction or dismissal, then late Gemini result, rule update, server replay, rollback, or account switch: user decision wins and stays in the right account.
11. Candidate learned from a few similar users, held-out near duplicates, different issuers, and historical negatives: no global promotion from correlated examples alone; evaluate field values and downstream totals.
12. Bad rule, malformed regex, JS/Dart mismatch, network loss, invalid checksum, stale client, or quota exhaustion: last valid behavior continues; job resumes or becomes reviewable; automatic rollback works.
13. Consent off or example deletion: user correction still applies locally/server-side; no cross-user training example or downstream bundle traceable to that user's data.

## 9. Metrics and completion definition

Track by family and rule version: coverage, exact field accuracy, auto-write precision, missed-financial rate, false promotion discard rate, Needs Review rate, correction/override rate, duplicate-event rate, bill-date errors, subscription false-series rate, rule shadow disagreements, rollback count, p95 intake-to-fact latency, Gemini jobs/tokens/429s, and device bundle adoption. Measure from independent labeled samples and user corrections; model confidence alone is not a metric.

The work is complete when a new eligible SMS format can be learned, evaluated, staged, promoted, downloaded, and, if it regresses, rolled back **without an admin action**; the same stored facts drive all relevant app projections; and all compatibility/scenario gates pass. If any family lacks enough evidence, it should continue through current rules, Gemini, or Needs Review instead of claiming autonomous accuracy.

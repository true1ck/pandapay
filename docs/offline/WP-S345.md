## S3 budgets (`api/src/budgets_write.js`)
`POST /budgets` body: existing fields plus optional `id` (uuid) and `clientEditedAt` (ISO UTC, e.g. `2026-11-13T10:00:00Z`). Bad `id` -> 400 `invalid_id`; bad clock -> 400 `invalid_client_edited_at`.
- Same `id` already owned: `200 {budget, replayed:true}`.
- Otherwise a per-target advisory lock is taken. If any budget row for that target (active, replaced or deleted) has a `client_edited_at` newer than the request, the incoming row is stored **inactive** and the reply is `200 {budget, superseded:true}`; the newer active budget is never touched. Else the old active row is deactivated and the new one inserted: `201 {budget}`. Equal clocks: the incoming request wins.
- `scope:'tag'` with an unknown/archived tag: `422 {error:'tag_unknown'}` (was 404 `tag not found`). Category/card unknown stay 404.
- `idx_budgets_one_active_per_target` is untouched.

`DELETE /budgets/:id` accepts header `X-Client-Edited-At` (ISO). If the active budget's `client_edited_at` is newer: nothing is deleted, `200 {superseded:true}`. Otherwise it deactivates as before (`200 {ok:true}`) and stamps the header value on the row, so a later *older* `POST` for the same target cannot resurrect it. A second delete is still 404. Invalid header -> 400.

## S4 recurring (`api/src/recurring_write.js`)
`POST /recurring` body: existing fields plus optional `id`, `clientEditedAt`.
- Without either: `201 {id}` exactly as before.
- With either: `201 {id, series}`; `series` = `{id, merchant_key, display_name, typical_amount_inr, cadence_days, next_expected_on, autopay_status, is_active, dismissed_at}`. The `ON CONFLICT (profile_id, merchant_key)` upsert is kept, so if a series for that merchant already exists under another id the **existing id is returned: the client must adopt `series.id`**.
- Same `id` replay: `200 {series, replayed:true}`.
- A series whose `dismissed_at` **or** `client_edited_at` is newer than `clientEditedAt` is not touched: `200 {series, superseded:true}`. A re-add with a later clock does resurrect it (as today).
`PATCH /recurring/:id`: non-uuid ids (`v2:abc`, `projection:x`) -> 400 `invalid_id` (verified by tests). Optional `clientEditedAt`: if the row's `client_edited_at` or `dismissed_at` is newer -> `200 {superseded:true}`; otherwise `{ok:true}`. Dismissed row with no newer-dismissal match keeps 404 `not_found`.
`POST /recurring/:id/dismiss`: unchanged (uuid guard already tested for `v2:abc` / `projection:x`).

## S5 append-only
- `POST /notifications`: optional `clientMutationId` (uuid) and `createdAt` (ISO, clamped in SQL to `[now-8d, now]`). With a mutation id: `INSERT ... ON CONFLICT DO NOTHING`; new -> `201 {notification}`, replay -> `200 {notification, replayed:true}` returning the stored row; a replay does **not** reset `read_at`/`created_at` and does not enqueue/send remote delivery again. If the same `dedupeKey` already exists under a different mutation id the stored row for that key is returned as a replay (the old title/body-refresh-on-dedupe is not applied on this path). Without a mutation id the `dedupe_key` upsert is byte-identical (the `client_mutation_id` key is stripped from the row). Invalid/unknown category -> `422 {error:'invalid_category'}` (list mirrors `notifications_category_check`). Bad id -> 400 `invalid_id`; bad `createdAt` -> 400 `invalid_created_at`.
- `POST /notifications/read` with a non-uuid `id` -> 400 (S0 guard, re-verified in `http_db_errors.test.js`).
- `POST /consents` moved to `api/src/consents_route.js` (`registerConsentRoute`). Optional `clientMutationId` (+ `clientRecordedAt`, accepted and ignored): `ON CONFLICT ... DO NOTHING`, replay -> `200 {consent, replayed:true}`; new -> `201 {consent}`. `granted_at` stays the server arrival time. The `sms_shared_learning` advisory lock is unchanged and the revoke trigger is `AFTER INSERT`, so it does not fire for a skipped conflict. Without the id the SQL is the old statement.
- `POST /sms-import-batches` (`api/src/sms_import_batches_route.js`): optional `clientMutationId`, same 201 / 200-replayed shape (`{smsImportBatch, replayed:true}`). The POST/GET now select explicit columns instead of `*` so the new column does not leak into old responses.
- `POST /support-tickets` (`support_tickets.js`): optional body `id` (uuid, else 400). With an id the insert is `ON CONFLICT (id) DO NOTHING`; a replay returns the same `201 {ticket}` shape (authenticated callers get the stored `created_at`) and **does not charge the limiter**; for a new row the limiter is charged after the insert and a refusal (429/503) rolls the insert back. Without an id: unchanged (charge, then insert). A present `Authorization` header that `optionalAuth` could not validate -> `401` instead of an anonymous ticket.

## Old clients
No new field -> same statuses and bodies, with these deliberate exceptions: unknown tag budget is 422 (was 404), invalid notification category is 422 (was 500), invalid `Authorization` on support tickets is 401 (was anonymous ticket).

## Known gaps / risks
- Handler tests use stateful fakes keyed on SQL text; real-Postgres behaviour (advisory locks, generic `ON CONFLICT DO NOTHING` across two partial indexes, RLS) is covered only by the PGlite SQL checks.
- Concurrent replays of one budget `id` for *different* targets are not serialised together; the primary key stops a duplicate (409 `duplicate`).
- Client follow-up (C7/C11): adopt `series.id` from `POST /recurring`; send `clientEditedAt` as the edit time (UTC); treat `superseded:true` and `replayed:true` as success.

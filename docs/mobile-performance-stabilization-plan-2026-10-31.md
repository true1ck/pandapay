Status: implementation in progress on `codex/ios-shortcuts-prototype`. The initial investigation was performed on `dev`; that branch was merged into the iOS prototype branch. ## 31 October profile update

The pictured PandaMark page is the Flutter `/splash` route. Its redirect waits for local session restoration and the onboarding preference, not the network token refresh. Three process-cold profile emulator runs after installing an instrumented dev APK resolved the splash at 5.39, 1.27 and 1.50 seconds from Dart `main`. In those runs the first Android secure-storage read completed at 5.21, 1.26 and 1.23 seconds; onboarding preferences completed at 1.54, 0.07 and 0.05 seconds. The first post-install run also had emulator startup stalls. This isolates a real wait in secure storage but does not establish that a physical release device has the same latency. Keep the authentication gate and measure a physical device before redesigning credential storage.

Initial implementation retains committed Activity and Spending content during same-query provider reloads, coalesces concurrent SMS lifecycle requests at the operation gate, and stops sync materialization from restarting the entire Home refresh. Profile-only startup timing and debug/profile SMS pass timing were added. These are scoped improvements, not completion of the DB worker, refresh ownership, or full performance acceptance work below.

## Executive diagnosis

The slowdown has two phases. Android's launch icon remains until Flutter's first frame. PandaPay then shows its own PandaMark route while local session and onboarding reads resolve. Once Home mounts, numerous independently owned jobs start or resume. Some are network asynchronous, but their response decoding, SQLite calls, JSON conversion, ranking and provider invalidations run on Flutter's UI isolate. `async` does not make that CPU or SQLite work concurrent with frame building. This is the leading architectural explanation for intermittent scroll hitches, though no current profile trace attributes a particular hitch to one stack.

On the installed `app.pandapay.pandapay.dev2` **debug** emulator build, process-cold `am start -W` samples were 6.65, 5.31, 2.94 and 3.22 seconds to Android's reported displayed frame. One earlier emulator-wide stall produced a 48.9-second outlier. Logcat recorded 32–64 skipped app frames around repeated first display. The first displayed frame is not necessarily first usable Home. A warm foreground `am start -W` reported 14 ms, showing that the expensive path is process cold. Android `gfxinfo` mainly sees Flutter's host view and is insufficient for Flutter scroll frame attribution. These numbers must not be treated as release performance.

The older 18 October investigation recorded a real production-device ANR before the SMS native worker fix. The follow-up architecture moved inbox capture to workers, batched acknowledgements and reduced some refresh amplification; its device check still noted 81 skipped startup frames. Do not reimplement those solved items without measuring the current path. Recent changes after that baseline added SMS repair/replay and AI work, automatic account recovery and more root lifecycle work. Git history establishes possible regression windows, not causation. The 18 October release-style 1.66-second activity check and today's debug measurements are not comparable baselines.

## Pipeline-specific findings to verify

### Separate SMS capture from transaction refresh

“Duplicate transaction refresh” means overlapping reads of the **app/backend transaction ledger**, not repeated full reads of the Android SMS inbox. The current SMS path already stores qualifying financial messages in `sms_captured_messages` and pending uploads in `sms_intake`. `sms_inbox_progress` stores the highest Android provider row `_id` per account namespace. Initial capture pages through the inbox; later checks read the newest ID and only query rows with ID greater than the durable checkpoint. The foreground/background SMS listener captures arrivals directly. Do not replace this with a date-only checkpoint: a delayed or backdated message can have an older timestamp but a newer provider ID. Advance the ID only after local capture commits; retain an idempotent source key because a broadcast and catch-up scan can see the same message. If the provider database is restored or its IDs reset, handle that as an explicit exceptional recovery policy, not routine full rescanning. Keep raw-message storage subject to the existing consent, retention and account-isolation rules; “store every SMS” would be broader than the app's financial-message capture contract.

The app transaction ledger has a separate flow: `homeDataRefreshProvider` invalidates `transactionsProvider`; `loadTransactionsWithOfflineCache` may independently fetch after returning a cached snapshot; `SyncEngine._materialize` can fetch all transactions after a sync pull and then invalidate `homeDataRefreshProvider`. Each result can reach `FinancialStore.saveTransactions`, where synchronous SQL/JSON runs on the UI isolate. This is the strongest current cross-page lag hypothesis. The standard target is one account-scoped transaction refresh owner with single-flight requests, an explicit freshness policy, durable writes, change-set publication and no broad refetch after sync already materialized the same entity.

1. `smsBackgroundFlushProvider` has four normal triggers: account namespace change, connectivity regain, resume, and a two-second startup timer. It also runs a full `flushAndRetry` every 90 seconds. The pass serializes itself, but a trigger during a pass sets `rerunRequested`, so closely spaced startup/resume events can cause a second full pass rather than being eliminated. Measure pass counts and reasons; the periodic trigger should only do work whose state is due.
2. Each full SMS pass can fetch the rule bundle, check the inbox head, drain pending SMS, attempt historical repair/replay if its per-account flag is absent, reconcile AI review, and fetch review rows again. `reconcileAiNeedsReview` reads all review items and may make a per-item job-status request; queued/processing items also schedule a four-second poll. This is appropriate for in-flight work but needs bounded item counts and a terminal-state filter. No current trace establishes that this is the observed hitch.
3. The SMS capture path normally uses a dedicated isolate and 25-row inbox pages. That is an existing protection. If the worker fails, `_captureMessages` falls back to `captureDirect()` on the UI isolate, which may perform synchronous parsing and SQLite writes. Count fallbacks in redacted diagnostics and inspect their root errors; do not remove the fallback before ensuring durable capture.
4. `SyncEngine` prevents overlapping *sync cycles* with `_running`, but it does not coordinate its full-history transaction materialization with Home refresh or the transactions provider. `SyncEngine._invalidateFor` invalidates `homeDataRefreshProvider`, potentially causing another broad fetch immediately after materialization. A changed row can then trigger further report/provider rebuilds. Trace request IDs and invalidation generations to prove the amplification on a real account.
5. `FinancialStore.saveTransactions` still loops all returned rows and queries existing rows for complete-query reconciliation using synchronous `sqlite3` on the UI isolate. `ResponseCache.put` may decode card JSON and update card entities synchronously before storing the blob. The volume of history, not merely the number of network calls, determines pause risk.
6. The automatic account-recovery provider runs an immediate check and minute timer when enabled. It may create a full account snapshot after server consent. Verify opt-in state and trace its CPU/DB work separately; avoid assuming it is active for every user.

### Trace fields and decision rules

For each job record `job`, `trigger`, account-safe generation, start/end, queue wait, network duration, response bytes, rows read/written, UI-isolate CPU span, DB lock wait, invalidated entities and outcome. For SMS record inbox head/checkpoint and count of *new* provider rows, pending queue count, AI in-flight count and worker-fallback count; never log raw message content. Correlate with Flutter frame timestamps. Prioritize a fix only when it explains a meaningful share of launch-to-usable time, slow frames, repeated requests or battery/network use. This prevents changing the established listener/checkpoint design without evidence.

## Work packages for parallel engineering

### P0 — Measurement contract and regression baseline (agent A: mobile performance)

1. Add low-overhead timestamps for Android activity creation/engine ready, Dart `main`, first Flutter frame, `TokenStore.load`, onboarding read, router redirect to Home, first Home frame and first responsive interaction. Redact identifiers and tokens.
2. Add `FrameTiming` collection and named timeline spans for DB open, transaction fetch/parse/save, SMS reconciliation, sync materialization, provider refresh and Home ranking. Include operation ID, row count and trigger; no SMS bodies or financial payloads.
3. Run profile build on emulator and a representative physical Android device with existing account data preserved. Collect at least 10 process-cold and 10 warm starts, 5-minute idle/scroll/resume sessions, online/offline, small/large history and pending SMS backlog. Record p50/p95, frame UI/raster percentiles, missed frames, peak memory, CPU and request counts. Capture an APK/source revision and environment fingerprint.
4. Compare a known-good commit or retained release on **equivalent** account size/device/network/build mode. Never clear user data or downgrade an active account for the comparison.

Exit: a trace identifies the dominant time slices before first frame and before usable Home, and attributes scroll stalls to UI-isolate, DB, network-completion or OS work. If the debug-only symptom disappears in profile/release, document that before changing architecture.

### P0 — Startup gate and service scheduling (agent B: app bootstrap)

Own `main.dart`, `router.dart`, session/token/onboarding boot path. Await A's trace contract, then remove measured pipeline work from first-frame construction. Keep authentication, maintenance/version and biometric lock correctness. Start optional root services after first usable frame with bounded scheduling and a lifecycle owner; push/recovery/location must still initialize when required. For token restore, evaluate parallel secure reads or a storage API that reads both at once, preserving migration and security semantics. Do not route to Home based on an unverified token or bypass lock to improve a metric.

Exit: lower first-frame and splash-to-Home p95 on the same profile/device matrix; signed-out, stale-token, offline, onboarding, biometric and deep-link flows remain correct.

### P0 — One refresh scheduler and request deduplication (agent C: data orchestration)

Own `homeDataRefreshProvider`, display lifecycle and interactions with sync/SMS invalidation. Establish one account-scoped generation/trigger scheduler for launch, resume, reconnect and mutation. Deduplicate identical in-flight endpoint requests; avoid duplicate full-history fetch from Home, transaction provider and sync materialization. Prefer entity-specific refresh and publish changed snapshots only. Bound concurrency and delay nonessential refresh until after Home interaction is ready; keep cached Home visible and stale-state semantics explicit. Define cancellation/account-switch fencing and retry/backoff. Coordinate contract with D and E before edits to shared `providers.dart`.

Exit: trace shows one initial fetch per required resource, bounded requests on resume, no stale-account publication, and fewer rebuilds without stale financial displays.

### P0 — DB and projection worker (agent D: local data)

Own `AppDatabase`, `FinancialStore`, transaction snapshot decode/save and query paths. Profile before changing. Move measured long SQL/JSON/parse work to a dedicated DB isolate or short bounded batches with explicit commit/change notifications; a synchronous `sqlite3` call inside `Future` remains synchronous on the calling isolate. Use targeted queries and indexes rather than scanning all account rows for a small update. Preserve SQLite transaction atomicity, WAL/recovery fencing, receipt idempotency, pending edits, account isolation and sync cursor ordering. Ensure a worker connection has clear lifecycle and cannot publish old-account results.

Specific register items: D01–D04. Move `_repairProvisionalMerchantNames`, `_deleteProvisionalDeclineTransactions` and versioned AutoPay repair out of ordinary reads. Coordinate migration triggers with E; never silently stop a repair merely to gain speed.

Exit: large-history save/read has bounded UI-isolate spans and stable frame times; replay, delete, offline, recovery and concurrency regressions pass. Do not merely lower `busy_timeout` again: that changes failure timing, not underlying work.

### P0/P1 — SMS, sync and recovery budgets (agent E: background pipelines)

Own SMS lifecycle, sync engine, optional automatic recovery. Instrument every trigger and pass outcome. Separate inbox-head check, pending-upload retry, one-time repair, AI polling and rule-bundle refresh so the 90-second timer cannot rerun the full pipeline when nothing is due. Bound review-job polling and account-history repair work. Investigate any worker-to-direct-capture fallback. Coordinate SMS upload, sync materialization and Home refresh through C's scheduler. Keep capture durability, progress checkpoints and retry on resume. For automatic recovery, verify that opt-in snapshot creation does not run on the UI isolate during interactive periods; rate limit and schedule appropriately. FCM 502 belongs to backend reliability separately; don't treat its HTTP wait as a proven UI block.

Specific register items: M01–M05 and X01–X03. Coordinate N01 notification scheduling with C so a wallet refresh does not trigger a redundant nine-check sweep. Preserve initial import, live listener, provider-ID checkpoint and durable upload queue.

Exit: a large inbox/long-absent account remains scrollable during reconciliation; no lost/duplicate transaction or skipped cursor; background work eventually completes and survives process death.

### P1 — Backend payload and observability (agent F: API/operations)

Measure `/transactions`, `/home-summary`, catalogue, SMS and sync response sizes and latency without private payload capture. Add pagination/delta or compressed transport only where client traces show payload transfer/parse dominates. Ensure retry storms are bounded and investigate recurring `/notification-devices` 502 separately. A faster server response alone will not fix synchronous Dart SQL/JSON after arrival.

Specific register items: B01–B02. Agree on a transaction delta/cursor contract with C/D before changing the API.

Exit: request fan-out, payload bytes, server p95 and failure/retry counts fall without missing history or breaking offline sync.

## Integration order and acceptance

A runs first and provides a shared trace schema. B can work after the startup baseline. C defines the scheduler contract before D/E alter shared invalidation paths; D and E can then work in parallel on separate files. F can profile API independently. Integrate one package at a time and rerun identical workloads after each; keep scoped commits and do not stage unrelated working-tree changes.

Set performance budgets from the profile baseline and supported device tier, then target a material improvement in p95 cold-to-usable-Home, no visible multi-second icon hold on representative devices, and smooth scrolling at the device's refresh rate. Track p99 long frames and ANRs, not only average FPS. Release gate: cold/warm/offline/resume tests on existing data, large inbox/history, account switch, biometric, background SMS, failed network, recovery and core financial invariants. Verify debug and release separately; judge user experience from profile/release. Roll out gradually with redacted timing/error counters and an easy rollback for scheduling changes.

## Standard Flutter approach and cautions

Use Flutter DevTools Performance and CPU views in **profile mode** to identify UI-isolate stalls and correlate them with pipeline timeline spans around a reproducible gesture. Keep frame-critical builds cheap and provider updates narrow. Use isolates for substantial pure-Dart parsing or a worker-owned DB connection, accounting for isolate startup and transfer overhead. Official references: [Performance view](https://docs.flutter.dev/tools/devtools/performance), [Performance best practices](https://docs.flutter.dev/perf/best-practices), [Isolates](https://docs.flutter.dev/perf/isolates).

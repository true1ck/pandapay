# Phone encryption format consumer inventory — 26 October 2026

This inventory is the compatibility prerequisite for the opt-in versioned phone-field writer in `auth/src/utils/fieldEncryption.js`. The implementation leaves the legacy writer as the default; it adds no migration, backfill, key generation/rotation, customer password, or database change. Do not enable `ENCRYPTION_V2_WRITES_ENABLED` until every deployed reader and restore consumer below has the selected key in `ENCRYPTION_READ_KEYS_JSON`, and the separate release proof is accepted.

## Stored field and format contract

- The auth database stores user and OTP `phone_number` values as either recognized legacy plaintext during migration or an authenticated AES-256-GCM envelope. Legacy envelope is `base64(iv):base64(tag):base64(ciphertext)` and must continue using the original `ENCRYPTION_KEY` bytes.
- The already implemented v2 reader accepts `v2:<key-id>:<canonical-base64-iv>:<canonical-base64-tag>:<canonical-base64-ciphertext>`. AAD is `pandapay-field-encryption-v2\0` followed by UTF-8 key ID. V2 keys come only from `ENCRYPTION_READ_KEYS_JSON`, an allowlisted list of at most eight unique IDs and canonical base64 32-byte keys. Unknown IDs, malformed envelopes, authentication failure, oversized envelopes, and invalid UTF-8 fail closed.
- Phone entry points normalize to international phone syntax before writing. `auth/src/routes/authRoutes.js` validates E.164 `+` plus 1–15 digits (maximum 16 ASCII bytes); contact replacement has the same maximum. The envelope writer independently caps encoded output at 4096 UTF-8 bytes, including key ID and separators. The remaining general `encryptField` alias must reject a v2 envelope that exceeds that cap rather than write an unreadable value.
- Equality lookup is separate: `auth/src/utils/encryptedPhoneSearch.js` canonicalizes phone input and derives the stable HMAC-SHA256 digest `pandapay-phone-lookup:v1:<canonical-phone>` using `PHONE_LOOKUP_HMAC_KEY`. No v2 writer change may touch this digest, its key, existing hash columns, indexes, OTP budgets, uniqueness, deleted-contact reuse, or active identity mapping.

## Write rollout contract and stop conditions

`ENCRYPTION_V2_WRITES_ENABLED` is a strict optional boolean: absent means legacy writes; only literal `true` or `false` is accepted when set. With `false`, an unused `ENCRYPTION_WRITE_KEY_ID` is ignored for compatible pre-provisioning. With `true`, startup requires existing `ENCRYPTION_ENABLED` and valid original `ENCRYPTION_KEY`, plus an `ENCRYPTION_WRITE_KEY_ID` that already exists in the validated `ENCRYPTION_READ_KEYS_JSON` map. The writer does not create a key or mutate configuration. It uses a fresh random 12-byte IV and the v2 reader's exact AAD/envelope contract; format/key metadata accessors return only a nonsecret format label and key ID.

Stop before enabling v2 writes if any auth instance, migration runner, restore/failback process, supported client path, or admin operation lacks a tested v2 reader/contract; if the original legacy key cannot be retained; if HMAC lookup or row identity changes; if any encrypted value cannot be read; or if restore would need to replace/rewrite records. Keep legacy writes until a later separately reviewed activation. A writer-only flag is not permission to backfill or rotate existing rows, and a successful local mixed-format test is not actual-data/provider acceptance.

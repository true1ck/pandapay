# Main PandaPay iPhone SMS implementation

Implementation started 30 October 2026 on `codex/ios-shortcuts-prototype`, following the [execution plan](ios-sms-intake-implementation-plan-2026-10-30.md). This is the real `app.pandapay.pandapay` application, using `lib/main.dart`. The prototype remains installed separately and its Shortcuts are not modified automatically.

## Implemented

| Area | Implementation |
| --- | --- |
| Native receiver | Nine main-target App Intents in `app/ios/Runner/IncomingSmsIntent.swift`: seven background-only actions, conditional foreground History Capture on iOS 26, and foreground History Finish. Capture body/sender remain optional text and original Date remains optional, preserving saved main-app bindings. History Capture has no Repeat Index input; legacy Window Capture retains it. Only an in-memory app-issued interactive launch can admit early foreground return; daily/cold captures stay quiet. Disabled/signed-out live capture returns `capture_disabled` without creating routine error notifications. Storage failures do not return a saved acknowledgement. |
| Durable handoff | `IncomingSmsSpool.swift` owns a private SQLite acquisition database under Application Support, excluded from backup. Serialized write transactions coordinate separate native callers; input is bounded to 20,000 UTF-16 units, 10,000 pending rows and 24 MB of pending body bytes. Pending content is never evicted to make space. iOS file protection permits access after first unlock; before-first-unlock execution remains a device test. |
| Security policy | Native security filtering was extracted to `SmsSecurityPolicy.swift` and remains checked against the existing shared synthetic corpus. Sensitive bodies are never retained for receipt counters. |
| Ownership | Explicit SMS enablement binds captures to the signed-in namespace and a random generation. Sign-out, disable, account switch, confirmed data reset and account restore revoke pending input and issued attempts. Cold intent delivery does not depend on Flutter restoring authentication first. |
| Shared processing | `IosSmsIntakeController` drains at most 50 rows per work unit through `SmsAutoImportController.captureShortcutMessages`, the existing rule/account state and `SmsCaptureWorker`. Valid non-sensitive inputs with a missing sender are retained without fabricating bank headers. The shared store routes unknown-sender financial candidates to local Needs Review, without automatic financial effects or upload. Probe inference stays available only to diagnostic callers. |
| Replay | Financial identity remains the shared account/sender/body source hash. Verified original-date acquisition uses a separate occurrence fingerprint. Estimated Current Date is not a verified occurrence identity. Local acquisition receipts commit before native acknowledgement; pending HTTP upload is a separate state. Reacquisition preserves existing retry attempts/backoff. |
| Worker safety | Large Shortcut batches cannot fall back to synchronous UI-isolate parsing. An admitted native writer is not abandoned on a timeout or disposal; recovery waits for its completion/exit rather than racing a late commit. |
| History | User selects 3/6/12/24 months or custom dates. App-owned, persisted calendar windows freeze the cutoff. A rolling two-year interval can span 25 calendar months. Empty windows do not stop the job. Pause/resume/stop, retry and explicit dense-window splitting retain progress and logical-month identity. |
| Receipts and coverage | Native finish reconciles Find count, enumerated items, Limit-off evidence, validation outcomes and committed shared results. Partial/unknown source completeness cannot advance coverage. Catch-up advances only a contiguous completed receive range; older history remains a separate ledger. |
| Daily/app-open/manual | These enter one native persisted coordinator. Catch-up includes the whole gap plus the previous calendar day of overlap. Resume notifications coalesce. A five-minute no-op guard prevents immediate endless overlapping jobs after completion. Daily automation setup is optional and user controlled. |
| Nonblocking UI | The main shell displays cached data normally and reserves space for `SmsSyncStatusBar`; no navigation gate or full-screen import spinner is added. Setup is available from iOS onboarding and Import & Sync. Continue/Pause/Retry do not own the durable job. A user-started session advances completed windows through Apple’s x-callback URL flow; ordinary app-open processing does not start a session. |

The acquisition database has a schema version and migrates old receipt/window metadata transactionally. Legacy Window Capture binds Repeat Index to its input fields, rejecting a changed item under an old index. Probe-style History Capture derives its receipt identity inside PandaPay from validated original fields; replay/reordering cannot inflate its unique source count. The independent Find count still gates completion, and indistinguishable source rows remain partial rather than falsely complete. Native snapshots expose only bounded recent job metadata; raw input is read through bounded drain calls and cleared after acknowledgement.

**Live:** keep the tested single-space Message Contains trigger. Replace the prototype action with **Capture Incoming SMS in PandaPay**. Map the incoming Message's Content, Sender and Date separately. Sender is text. If using Current Date, leave **Date evidence = Estimated (Current Date)**; select **Original Message Date** only when passing the source Message Date.

**History:** use one production recipe, default name **PANDAPAY SMS HISTORY** (editable in setup). Preserve its original Shortcut Input as the version-3 **Import request** variable throughout the entire recipe.

1. **Begin PandaPay SMS Window** with that request.
2. **PandaPay SMS Window Start** and **PandaPay SMS Window End** with the same request.
3. Find Messages using those dates, Limit off, no text/sender filter. The start action supplies a one-second query superset; native capture enforces the exact start-inclusive/end-exclusive issued interval.
4. Repeat each returned Message: **Capture PandaPay History SMS** receives the request and that Message's Content, sender text and original Date. It has no Repeat Index field; receipts are derived inside PandaPay. The older **Capture PandaPay Window SMS** remains compatible with its existing text sender and Repeat Index mappings. Both use the production capture store. Do not reuse independently reordered arrays or the output of the preceding action.
5. For app-started interactive history, **Finish PandaPay History Import** receives the request and Count of all Find results and opens PandaPay, matching the working probe's completion mode. This foreground variant is currently under device privacy qualification. The existing **Finish PandaPay SMS Window** remains quiet for background copies. Set **Find Messages limit is off** to Yes only after checking it; set **Search may be incomplete** when applicable. Results at or above 2,000 items require attention/splitting rather than a claim of exhaustive acquisition. Bind Stop and Output to the chosen Finish action's result.
6. Start the chosen period once from **Start import**. The app uses `shortcuts://x-callback-url/run-shortcut` and receives a nonce-scoped `pandapay://sms-import/…` return. It drains and reconciles the current window before opening the next one, while foregrounded, within the same user-started job. **Pause**, cancellation, failure, partial results or account changes stop progression. After an interruption or app restart, **Resume import** issues a fresh attempt for unfinished windows. Financial replay remains idempotent.

**Optional daily automation:** Time of Day → **Prepare PandaPay SMS Catch-up** → if output is nonempty, Run Shortcut a background copy of the history recipe with that output as input. Use quiet **Capture PandaPay History SMS** and **Finish PandaPay SMS Window**. Existing background copies using the indexed Window Capture remain compatible. This does not create an invisible direct Messages API. A native-only handoff can remain saved for processing until the app has runtime; finishing acquisition is not transaction creation. No user automation has been added or changed by this implementation.

The setup screen includes these instructions. Keep the prototype until the production recipes have been exercised without depending on it.

No callback means no repeated app-switch loop and no false completion.

### Return to PandaPay while interactive capture runs

The new implementation uses iOS 26's supported background + dynamic-foreground execution mode for the existing **History Capture** action, preserving every published input name/type, result type and default `openAppWhenRun=false`. After an input is durably saved, the current in-memory app-issued launch may consume one foreground-return budget using `continueInForeground(alwaysConfirm: false)`, and only when the system context says foreground continuation is available. The budget is absent for daily/manual/cold invocations, is consumed once rather than for every SMS, and is re-armed only when PandaPay deliberately resumes that same runner. A refused/unavailable foreground transition does not roll back the captured input. Pre-iOS-26 execution retains the existing background/Finish behavior. `alwaysConfirm=false` lets iOS avoid an extra prompt after recent interaction; it is not a promise that iOS can never ask.

While a user-started session is active, a **five-second gap without new receipt progress** can resume the **existing** Shortcuts runner from PandaPay, even if that month is still running. Native storage rechecks the current state, account/attempt and the exact unchanged received count before opening the public `shortcuts://` destination. This is stall recovery, never a Finish call or proof that a month ended. New receipt progress restarts the interval; the same count can admit at most one recovery so unavailable data/permission cannot produce an endless switching loop. The next month still needs committed counts/processing and the matched real callback. Completed-month callback recovery keeps its existing separate bounded path. Pauses, account changes, cancellation/errors, disabled capture, background state and disposal stop the inactivity recovery. Native ephemeral foreground/callback state is also revoked when a job is replaced, controlled or reset.

Tests cover quiet/no-budget and one-return-per-burst presentation policy, stale-count native rejection, partial/running admission without false completion, five-second timing, timer reset on receipts, unchanged-progress loop prevention, background/interruptions and automatic next-month callbacks. **43 focused Flutter tests** and the native harness passed; targeted analysis reported no issues. Actual foreground occupancy, any system prompt and multi-month progression must be qualified on the device before claiming a faster or fully quiet flow.

Apple references: [dynamic foreground execution](https://developer.apple.com/documentation/appintents/intentmodes/foregroundmode/dynamic), [foreground continuation and confirmation semantics](https://developer.apple.com/documentation/appintents/appintent/continueinforeground%28_%3Aalwaysconfirm%3A%29). Use this supported API rather than a private activation method or a background self-URL trick.

# Sync isolation and protected restore review — 25 October 2026

The next B02/LP01 slice is implemented and locally verified. Seven legacy SECURITY DEFINER sync signatures now check the backend's transaction-local profile context and the owned device, use an empty search path with qualified product tables, and lose their PUBLIC execute grant. The API role retains explicit execution. Existing URLs/signatures, IDs, keys and mobile defaults remain. **This source is not deployed and does not close LP01, B02 or the whole security plan.**

## What changed

New migration [20261025151350_legacy_sync_context_isolation.sql](../db/supabase/migrations/20261025151350_legacy_sync_context_isolation.sql), generated with the installed Supabase CLI, uses CREATE OR REPLACE for registration, legacy push, pull, acknowledgement, both private-category insertion overloads and merchant-rule sync. It rewrites no customer rows. Synthetic upgrade checks preserve all 153 non-ledger table fingerprints, sequence state across migration/replay and routine OIDs.

- All seven require a non-null profile equal to `pandapay.uid()` and an existing product profile. Calls that use a device require it to belong to that profile. Registration preserves its previous stale/foreign-device behavior: it creates a fresh owned device rather than adopting another user's row.
- Qualified relations and an empty search path prevent session temporary tables from shadowing product tables. Function owners are retained; the broader definer-owner privilege review remains open. PUBLIC execute is revoked with RESTRICT; explicit named grants are preserved for consumer review. Direct/inherited execution by `anon` and `authenticated` is now a strict policy failure for these routines and V2, even if PUBLIC has no grant.
- The legacy writer now also rejects raw transaction status changes/deletion in SQL, matching the API's existing domain boundary. It retains its existing typing behavior: numeric edits still need the default-off V2 path and its separate acceptance; this migration does not silently enable V2 or claim to fix clock-independent conflicts.
- Category ID collisions against another profile return `not_found` without appending a misleading successful change. Merchant category/flag actions and version checks remain intact. Acknowledgements remain monotonic; negative/null sequences or a historically inconsistent cursor owner are refused, preserving the row for review.

The custom `app.user_id` setting is trusted **only inside the backend's authenticated transaction**. A PostgreSQL setting is not a JWT verifier. Backend credentials must never be supplied to untrusted clients; named/direct/inherited grants and exposed-schema consumers still need actual-target acceptance. Guest/revoked/deleted-account rejection remains in existing API/auth/session/lifecycle controls; these SQL guards do not independently discover auth-service session state.

Sources: [independent-login integration fixture](../api/test/sync_isolation_postgres.js), [strict product privilege policy](../db/security/product-runtime-privileges.json), [privilege evaluator](../db/scripts/audit_runtime_privileges.js). PostgreSQL documents both the default PUBLIC function privilege and CREATE OR REPLACE's preservation of object identity/privileges; explicit revocation and consumer checks are therefore necessary. [Function security](https://www.postgresql.org/docs/17/sql-createfunction.html), [REVOKE](https://www.postgresql.org/docs/17/sql-revoke.html).

## Recovered migration history and actual-copy result

The protected local PostgreSQL17 restore's upgrade preflight detected **one applied migration absent from this checkout**: `20261023180000_user_merchant_rule_actions.sql`. Its original bytes were recovered from retained Git commit `c0112f7`; both function-body hashes exactly match the saved database's catalogue. [Provenance](../artifacts/security-sync-isolation-2026-10-25/recovered-migration-provenance.json). The new guarded merchant routine preserves those newer flag actions, avoiding a downgrade to the older category-only body. Recovering this SQL does not restore all app/API features from that other commit or enable new flag UI.

The saved ledger lacks checksums for most historical entries. Its independently reviewed baseline predates the recovered file; the missing-file stop must not be bypassed by deleting a ledger row, inventing a checksum or silently regenerating an approval baseline. The recovered file's complete original DDL still requires source/schema review, a refreshed independent baseline decision, then the full candidate upgrade on the protected current copy. **The actual-data upgrade has not passed.** Synthetic upgrade/restore success is separate.

A new optional read-only helper [review_restored_privileges.js](../db/scripts/review_restored_privileges.js) audits a verified paired local restore and compares its product ledger with source. `rehearse_local_backup.py --privilege-review` requires explicit product/auth role names, the same generated loopback restore pair, both exact-comparison attestations and encrypted output. It performs no grant, migration, application-function invocation, source connection or plaintext report write. Detail remains at `status/privilege-review.json.age` in the existing protected recovery folder. A completed audit can contain blocking findings; it is not strict acceptance.

The saved encrypted deployment configuration supplied role names privately; no live URL/provider credential was passed to the audit subprocess. The saved product and auth role matrices both still fail strict policy, including definer ownership/search paths/PUBLIC execution, migration-ledger access and privileged auth-role ownership/memberships. These findings are review leads in a historical restored copy, not new independent vulnerability counts or proof of current deployed configuration. [Count-only scoped summary](../artifacts/security-sync-isolation-2026-10-25/protected-privilege-findings-summary.json). Do not apply blanket grants/RLS/owner changes merely to reduce the counts.

## Engine compatibility experiment

The production app's dependency manifest/lock is unchanged. An isolated full-app candidate pinned `sqlite3` 3.5.2, removed `sqlite3_flutter_libs` in that copy and selected the maintained `sqlite3mc` native-assets hook. It built the dev debug APK; the agent's focused database/recovery tests passed. Version 3.8.0 did not resolve with the current Flutter SDK's pinned `meta` dependency, so it was not forced through an override.

The [package's versioned documentation](https://pub.dev/packages/sqlite3/versions/3.5.2) describes its native hook packaging and SQLite API. [SQLite3 Multiple Ciphers documentation](https://utelle.github.io/SQLite3MultipleCiphers/) describes its encryption and temporary-data limitations. The fixture explicitly selects ChaCha20 and memory temporary storage. Engine support/license/provenance and all signed-device migration cases remain acceptance work; a debug fixture is not a production encryption rollout.

## Recovery policy accepted by the user

The user approved automatic updates **after explicit recovery opt-in**, with existing phone/email OTP and **no extra password**. Uploads attempt at 15-minute intervals while the app is active and online, keeping the established two-copy/5 MiB/cooldown/global quota bounds. Data created offline and lost before successful sync/recovery upload is unrecoverable. The service can unwrap archive keys for OTP recovery, so this is not end-to-end encryption against the service operator.

Automatic writers never obtain escrowed archive keys. Recent OTP remains required for enrollment, key downloads/restoration and discard. A signed, current active-device session plus its exact consent generation authorizes automatic upload. Account switches/logout/revocation fail closed through existing current-session checks; the existing bounded auth cache is not an instantaneous universal revocation guarantee.
